## 0. 一句话结论

NexOS 现在**不是**一个现代意义上的多任务操作系统，而是一个**功能极其丰富的单地址空间裸机应用框架**：所有代码（内核、C# 桌面、PE 兼容层、AI 推理）都跑在 ring0、同一个 identity-map 地址空间、同一个不启用中断的轮询主循环里。它缺的不是"功能数量"，而是把功能变成操作系统的三条机制：**隔离、抢占式调度、资源虚拟化**。

那个 397 MB 的 GGUF 模型文件正是这个缺陷最集中的症状：因为文件系统装不下、没有按需分页、没有用户态服务、没有设备抽象，只能把数据用**硬编码 LBA** 直接焊进系统盘镜像，并在每次开机时由内核无条件整块读进 ring0 内存。

## 2. 与真正操作系统的差距

### 2.1 缺的是三条机制，不是功能

| 机制 | 真正的 OS 做什么 | NexOS 现状 | 直接后果 |
|---|---|---|---|
| **隔离** | ring0/ring3 分离、每进程页表、NX/SMAP、系统调用门、用户态不可触碰内核地址 | 全在 ring0、identity-map、无 per-process CR3；C# 与 PE 代码与内核同权 | 应用一个野指针 = 全机三重故障；无内存保护、无权限强制 |
| **调度** | 时钟中断驱动抢占、优先级/时间片、多核负载均衡、阻塞/唤醒、idle | 无 `sti`、无 IRQ、单主循环轮询；"进程"是协作式 CLR slot | 任意长任务（如 400 MB 模型加载、96 token 推理）**冻结整机**；无并发、无响应性保障 |
| **资源虚拟化** | VFS 抽象、按需分页/swap、块设备层与驱动模型、文件描述符、配额、缓存 | 硬编码 LBA、flat 文件系统、整块 `big_alloc`、PIO 轮询 | 换个模型要重建整张系统盘；大文件只能焊死在某个扇区 |

### 2.2 逐项差距矩阵

| 能力 | 现代通用 OS | NexOS | 差距等级 |
|---|---|---|---|
| 特权级 / 系统调用 | ring3 + syscall/MSR 门 + 参数拷贝校验 | 无用户态；icall 是 ring0 直接函数调用 | **根本性** |
| 虚拟内存 | 每进程地址空间、缺页、COW、mmap、swap、OOM | identity map、静态 PMM、无缺页处理 | **根本性** |
| 多任务 | 抢占式、多核、阻塞式 I/O | 单循环轮询、协作式 slot、AP 仅 bring-up 骨架 | **根本性** |
| 中断 / 驱动模型 | IRQ + 中断上半部/下半部、设备枚举、可加载模块、DMA 队列 | 无 IRQ；驱动全静态链入；ATA/PS/2 全靠轮询 | **根本性** |
| 文件系统 | VFS、日志、权限位/ACL、页缓存、崩溃一致性、配额 | SFS 只读 + MKFS flat 表（8 MiB）、无权限位/日志/缓存 | 大 |
| 存储容量 | 动态卷、分区表、LBA48、NVMe/AHCI 队列 | LBA28 + 双 IDE 通道、硬编码 LBA 布局 | 大 |
| 网络 | 完整 socket/TCP/IP 栈、网卡中断、多连接 | 模块已链接但未挂网卡；L5 未落地 | 大 |
| 安全模型 | 硬件强制 + capability/ACL + 审计 + 沙箱 | 应用层口令 + 软件约定式 token/边界检查 | 大 |
| 应用 ABI | ELF/PE 动态链接、libc/POSIX、进程隔离 | MiniCLR 32 位栈机（无泛型/异常/浮点/BCL）、PE 兼容层未接线 | 大 |
| 启动 / 配置 | bootloader 配置、initrd、ACPI/UEFI 服务、设备树 | 硬编码 LBA + 编译期常量；布局漂移曾多次导致静默损坏 | 中 |
| 可观测性 | 内核日志、tracing、procfs、崩溃转储 | 串口 DIAG step + 宿主侧脚本（属构建期外挂） | 中 |
| 功能广度 | 通用 | **极广**（GUI、AI 推理、C# 桌面、Win32 兼容、TLS、OS API） | NexOS 反超 |

### 2.3 定性

> **NexOS = 一个跑在 x86-64 long mode 的、单特权级、单线程、硬编码布局的裸机应用框架（bare-metal application framework），附带一个非常完整的 GUI/AI/托管运行时演示。**
>
> 它已经能"做很多事"，但还做不到操作系统最核心的那件事：**让多个互不信任的程序，在彼此隔离、可被抢占、资源可抽象的环境里同时运行**。

## 3. 模型文件：为什么它是架构缺陷的集中体现

### 3.1 当前物理布局（`os_v2.img`，约 429 MB / 409 MiB）

| LBA | 内容 | 大小 |
|---|---|---|
| 0 | MBR / `boot.bin` | 512 B |
| 1–32 | `stage2.bin` | 16 KiB |
| 拼接区 | `kernel32.bin`（前 4 MiB 内） | — |
| 2048 | `kernel64.bin` | ~1.3 MiB |
| 6144 | SFS（只读，桌面/mex/资源） | 9,218,048 B |
| 25600 | Linux 用户分区 `linux_sfs.img` | ~17.9 MB，末端约 LBA 60670 |
| **61440** | **模型描述符** `MINIMDL1` + u64 size + u64 start_lba | 512 B |
| **61441+** | **GGUF 裸 payload**（`qwen2-0_5b-instruct-q4_k_m.gguf`） | **397,805,248 B ≈ 379 MiB** |

→ 镜像 **92.7%** 是模型。`os_v2_vbox.vdi` 412 MiB、`data_vbox.vdi` 仅 7 MiB（MKFS 数据盘，IDE-1-0 / 0x170）。

### 3.2 构建链路

```
make build/os_v2.img MODEL_GGUF=build/qwen2-...gguf
  → cat boot/stage2/kernel32 ; truncate 4M ; dd kernel64 / sfs / linux_sfs
  → python3 tools/embed_model.py os_v2.img <gguf> 61440 61441
      → truncate 到 61441+776964 扇区 ; 写描述符 ; 循环 1 MiB chunk 写 397 MB
  → VBoxManage convertfromraw → 412 MiB 动态 VDI
```

### 3.3 运行时链路（每次开机无条件执行）

```
kmain64:8832 [AUTOTEST] probing embedded GGUF
  → model_blob_probe()  扫 4 个硬编码 LBA {61440,16383,8191,4095}，ata_read_sector(主盘)
  → model_blob_read()   virtio 1MiB 分块 / BM-DMA 16KiB 分页 / PIO 单扇区回退
                        big_alloc(397 MB)  ← 整块常驻 ring0
  → qwen_load(blob,size,512)  R.blob 常驻不释放
  → qwen_generate("DeepSeek is which company?", 96 tokens)
  → 之后才轮到 OSAPI 自测、GUI 登录、mforms_start
```
另有 4 处 `model_try_load()`（AI 命令、auto-ask 后门、终端命令等）。

### 3.4 由此产生的 8 个真实问题

1. **镜像 429 MB，其中 397 MB 是模型**；系统代码本体只有约 30 MB。
2. **每次构建都要往共享文件夹写 400 MB** —— 本轮 L4 构建就因此把 Linux 构建 VM 写挂（`Guest seems to be unresponsive`、SSH 握手超时），被迫硬断电重启。
3. **VDI 每次同步转换 412 MB**，构建—验证闭环长达 10–25 分钟。
4. **启动无条件加载 + 一次 96 token 推理**，串口要等数分钟才走到 OSAPI 自测；期间整机被冻结（无 IRQ）。
5. **397 MB 常驻 ring0 内存**，而验证 VM 只配了 1024 MB。
6. **换模型 = 重建并重新同步整张系统盘**，模型与内核镜像强耦合。
7. **LBA 61440 是硬编码逃生位**：Linux 分区末端约 LBA 60670，中间只剩 ~770 扇区余量；SFS 再长一点就会撞车（`Makefile:186` 的注释已经记录过一次这类事故）。
8. **描述符无版本、无校验、无设备号**（`MINIMDL1` 仅 8+8+8 字节），只能靠 4 个候选 LBA 猜位置；探测函数还写死在主盘 0x1F0。

## 4. 改造目标与硬约束

**目标**：把 397 MB GGUF 从 `os_v2.img` 彻底移出，使系统盘镜像回落到约 30 MB，模型成为可独立替换、可缺席、可按需加载的介质。

**硬约束**（改动不得破坏）：
- `make all` / `check-k64` 门禁保持 `0 (clean)`；
- MKFS 数据盘前 8 MiB 的格式与内容不变（Notepad 保存、桌面快捷方式、会话持久化、`ai_events.bin`/`ai_cmd.bin` 全部依赖它）；
- 已实机全绿的 OSAPI 自测（L0–L3、L12）不被破坏；
- **旧 429 MB 镜像仍可启动**（保留旧 LBA 探测做回退）；
- 没有模型时系统必须照常进桌面，不得打印 FAILED 或卡住；
- 不动默认同步/异步 PE 执行路径（兼容层骨架本就未接线，避免引入无关回归）。

## 5. 方案对比与推荐

> **歧义澄清**：「把模型文件移出」有两种解读。
> - **解读 A（工程层）**：移出 `os_v2.img` 系统盘 → 解决构建/同步/启动问题 → **本方案的范围**。
> - **解读 B（架构层）**：把 AI 推理栈整体移出 ring0、变成用户态服务 + 按需分页 → 那才是"真正 OS"的做法，但依赖 L4 内存层实机验证、L5 IPC、以及调度/隔离机制的建立，列为 P3。
>
> 下面按解读 A 评估；解读 B 作为方向写进第 7 节。

| 方案 | 做法 | 优点 | 代价 / 风险 | 结论 |
|---|---|---|---|---|
| **A. 新增第三块 VDI**（SATA-0-0 或 IDE-0-1 从盘） | 专门做一张 `model.vdi` 放裸 blob | 与系统盘、数据盘完全隔离，语义最干净 | VBox 配置的 SATA 是 AHCI，内核只有 PIO 0x1F0/0x170；挂 IDE 从盘要给 `ata_read_sector_base` 加 `drv=0xB0`；`vbox_sync.ps1` 要同步第三张盘 | 备选（中期最干净） |
| **B. 复用现有 IDE-1-0 数据盘的高 LBA**（推荐） | 把 `data_vbox.vdi` 从 7 MiB 扩到 512 MiB，MKFS 保持 LBA 900–16117 不变，模型放 LBA 20000+ | **零 VM 配置改动**；内核已有 `ata_fs_base=0x170` 的探测先例；`tools/make_data_vdi.py` 已有生成器；两盘同步链路现成 | 需扩展数据盘生成器与同步脚本；secondary 通道没有 BM-DMA/virtio 快速路径，须补批量 PIO；扩容会重建 MKFS（需备份/重放） | **第一阶段推荐** |
| **C. 直接做用户态服务 + 按需分页** | 模型放文件，推理进程 ring3 按需 mmap | 架构上正确，一步到位 | 当前无 ring3、无缺页、无 IPC、无调度器；等于先造半个 OS | 不作为本轮，列 P3 |
| **D. 宿主侧注入**（串口/virtio/9p） | 模型完全不进任何 VDI | 镜像最干净 | 无中断/无驱动框架，吞吐与复杂度都不可控 | 不推荐 |

**推荐 B 的理由**：它用现成的第二通道和现成的生成器，把"模型外置"与"架构重构"解耦，能在本轮就拿到 90% 的工程收益（镜像 429→30 MB、构建不再写 400 MB、启动不再强加载），且为 P3 留出干净的迁移路径。

## 6. 推荐方案 B 详细设计（待拍板后实施）

### 6.1 新磁盘布局

**系统盘 `os_v2.img`（IDE-0-0 / 0x1F0，约 30 MB）**：MBR → stage2 → kernel32 → kernel64@2048 → SFS@6144 → Linux SFS@25600。**删除 `embed_model.py` 调用与 LBA 61440/61441 常量**。

**数据盘 `data_vbox.vdi`（IDE-1-0 / 0x170，扩到 512 MiB）**：

| LBA | 内容 | 说明 |
|---|---|---|
| 900 | MKFS superblock `MKFS\x02` | **字节不变** |
| 901–916 | MKFS 文件表（16 扇区） | 不变 |
| 917–16116 | MKFS 数据区（15200 扇区） | 不变 |
| 16117–19999 | 保留区 | 给 MKFS 扩容留余量 |
| **20000** | 模型描述符 v2 `NEXMODL2` | 单扇区 |
| **20001+** | GGUF payload | 约 776964 扇区，末端约 LBA 796965（< 1,048,576 = 512 MiB） |

### 6.2 描述符 v2（单扇区，向后不兼容旧 magic）

```c
struct ModelDescV2 {
    char     magic[8];      // "NEXMODL2"
    uint32_t version;       // 2
    uint32_t header_size;   // sizeof(ModelDescV2)
    uint64_t size;          // payload bytes
    uint64_t start_lba;     // 相对本盘的 LBA
    uint16_t io_base;       // 0x1F0 / 0x170
    uint8_t  drive;         // 0xE0 master / 0xB0 slave
    uint8_t  flags;         // bit0: lazy, bit1: verified
    uint32_t crc32;         // 描述符 + payload 头部 4 KiB 校验
    char     name[48];      // 便于串口打印与换模型核对
    uint8_t  reserved[432];
};
```
旧 `MINIMDL1` 探测列表保留，用于回退到老镜像。

### 6.3 内核改动清单（`.attic64/kernel64.cpp`）

| 函数 / 位置 | 改动 |
|---|---|
| `ata_read_sector_base(base,lba,buf)` (:427) | 增加 `uint8_t drv` 参数（默认 `0xE0`），`outb(base+6, drv \| ((lba>>24)&0x0F))`；现有调用者行为不变 |
| `ata_read_multi()` (:466) | 把硬编码 `0x1F0/0x1F7` 提取为 `base` 参数，供 secondary 批量 PIO 使用（400 MB / 128 扇区 ≈ 6070 次命令，远优于 777k 次单扇区） |
| `model_blob_probe()` (:4604) | 改为返回 `ModelLoc{io_base, drive, lba, size}`；候选表扩为 `{(20000,0x170,0xE0), (61440,0x1F0,0xE0), 旧 3 个}`；校验 magic/version/crc32/size 上界 |
| `model_blob_read()` (:4622) | 接收 `ModelLoc`；**secondary 通道禁用 virtio/BM-DMA 快速路径**（两者都绑定 primary 设备），改走批量 PIO；primary 保留原三条路径 |

## 9. 风险与待拍板

**风险**
- `ata_read_sector_base` 加 `drv` 参数会触及所有 ATA 调用者（SFS/MKFS/诊断扇区/32 位切换），回归面较大，须配合 P0 的固定基线；
- VBox PIIX3 的 secondary 通道没有可用的 BM-DMA / virtio 快速路径，若批量 PIO 未落地，手动 `model load` 会明显变慢；
- 数据盘扩容会重建 `data_vbox.vdi`，其中现有用户会话/快捷方式需先备份或重放；
- 当前工作区存在并行 `make play` 进程与镜像中间态（见第 10 节），改造前必须先收敛。

**待你拍板**
1. 「移出」按解读 A（移出系统盘，本方案）还是直接上解读 B（移出内核态）？
2. 目标介质：复用 IDE-1-0 数据盘高 LBA（推荐）／新增 IDE-0-1 从盘／新增第三张 VDI？
3. 是否保留开机自动推理自测？（建议关，改为 `model load` 手动 + `NEX_MODEL_LAZY=0` 可恢复）
4. L4 内存层实机验证尚未完成：先补完并固定基线，还是与 P1 合并构建？
