## 1. 一句话结论

**模型已从系统盘移到数据盘，系统镜像 429 MB → 31 MB，开机不再强加载 379 MB 权重。**
同时修掉了三个此前一直存在、但被「看起来是绿的」掩盖的缺陷。

## 2. 磁盘布局（最终形态）

### 系统盘 `build/os_v2.img`（IDE-0-0 / 0x1F0，约 30 MB）

| LBA | 内容 |
|---|---|
| 0 | MBR |
| 1 | stage2 |
| 2048 | kernel64.bin |
| 6144 | SFS |
| 25600 | Linux 用户分区 |

**不再有模型段。** `Makefile` 的 `$(IMG)` 规则已删除 `embed_model.py` 调用。

### 数据盘 `build/data_disk.raw` → `build/data_vbox.vdi`（IDE-1-0 / 0x170，512 MiB）

| LBA | 内容 |
|---|---|
| 900 | MKFS superblock `MKFS\x02`（**与改造前逐字节一致**） |
| 901–916 | MKFS 文件表（16 扇区） |
| 917–16116 | MKFS 数据区（15200 扇区） |
| 16117–19999 | 保留区 |
| **20000** | **`NEXMODL2` 描述符**（单扇区） |
| **20001–796964** | **GGUF payload**（397,805,248 B） |

MKFS 区域用 `--seed` 从**当前在线的数据盘**播种，因此用户数据（实测 70 个文件：
会话、快捷方式、保存的文件）完整保留。

## 3. 描述符 v2（`NEXMODL2`）

```c
struct ModelDescV2 {        // 恰好 512 字节 = 一个扇区
    char     magic[8];      // "NEXMODL2"
    uint32_t version;       // 2
    uint32_t header_size;   // sizeof(ModelDescV2) = 512
    uint64_t size;          // payload 字节数
    uint64_t start_lba;     // payload 起始 LBA
    uint16_t io_base;       // 0x170 = secondary
    uint8_t  drive;         // 0xE0 = master
    uint8_t  flags;         // bit0 lazy
    uint32_t crc32;         // payload 头 4 KiB 的 CRC-32
    char     name[48];
    uint8_t  reserved[424];
};
```

旧 `MINIMDL1` 描述符仍在探测表里，所以**旧的 429 MB 镜像仍可启动**。

### 探测候选表

```c
{ ATA_SECONDARY, 0xE0, 20000 },   // 数据盘（新的家）
{ ATA_PRIMARY,   0xE0, 61440 },   // 旧系统盘内嵌（兼容）
{ ATA_PRIMARY,   0xE0, 16383 },
{ ATA_PRIMARY,   0xE0, 8191  },
{ ATA_PRIMARY,   0xE0, 4095  },
```

## 4. 内核改动

| 位置 | 改动 |
|---|---|
| `ata_read_sector_drive(base, drv, lba, buf)` | 新增 drive-select 参数；`ata_read_sector_base` 保留为 0xE0 包装层，**所有旧调用点行为不变** |
| `ata_read_multi_drive(base, drv, lba, count, buf)` | 任意通道批量 PIO；`ata_read_multi` 保留为 primary 包装层 |
| `ata_soft_reset_base(base)` | 任意通道软复位（0x376 / 0x3F6） |
| `model_locate(ModelDesc*)` | 跨盘探测 + v1/v2 描述符解析 |
| `model_blob_read_desc(ModelDesc*)` | 按描述符读；primary 走 virtio/BM-DMA，secondary 走数据盘路径 |
| `model_read_data_disk()` | secondary 读取：**先做一次 8 扇区批量探测**，失败则软复位并回退单扇区 PIO |
| `crc32_bytes()` | 描述符 CRC-32 校验（与宿主 `zlib.crc32` 同算法） |
| `kmain64` AUTOTEST | 改为只打印描述符信息；`NEX_MODEL_LAZY=0` 时恢复开机加载 + 推理 |
| `cmd_model load/status` | 改用 `model_locate`，提示语指向数据盘 |
| `model_try_load()` | 按描述符定位；记录 `g_model_alloc` 供 `model unload` 精确释放 |

### 为什么 secondary 不用 BM-DMA

BM-DMA 在这套代码里是**硬绑 primary** 的：`ata_read_dma_page()` 直接写死
`0x1F6/0x1F7`，`g_bm_base` 也只探测 primary 的 bus-master。
PIIX3 的 secondary bus-master 在 0xD0，要参数化需要重写整条 DMA 路径
——而这条路径历史上踩过三次 VirtualBox 崩溃（PRDT EOT 位错误等），
不值得在本轮冒险。

### 为什么不用无条件批量 PIO

代码里有一条实测注释：

> VirtualBox's PIIX3 IDE wedges on a count>1 READ SECTORS command
> (BSY/DRQ never clear), so `ata_read_multi()` is deliberately NOT used.

所以数据盘读取**先探测后决定**：一次 8 扇区批量命令 + GGUF magic 校验，
通过才用批量（128 扇区/次），否则软复位并全程走单扇区 PIO
（SFS 用的就是这条路径，在 QEMU / VirtualBox / VMware 上都验证过）。

## 5. 构建与宿主侧改动

| 文件 | 改动 |
|---|---|
| `Makefile` | 删除 `$(IMG)` 里的 `embed_model.py`；新增 `MODEL_LBA`/`DATA_DISK_MB`/`NEX_MODEL_LAZY`；新增 `model-pack` 目标；`kernel64.o` 编译行加 `-DNEX_MODEL_LAZY=` |
| `tools/make_data_disk.py` | **新建**。产出**裸镜像**（RAW），流式写入，1.5 秒生成 512 MiB，宿主内存占用 < 1 MiB |
| `tools/check_data_disk.py` | **新建**。校验描述符 magic/version/header_size、GGUF magic、头部 CRC、MKFS 区是否保留 |
| `tools/sync_data_disk.ps1` | **新建**。`convertfromraw` → 保留 UUID → 交换 → 重新挂载 |
| `tools/vbox_check.py` | 重写为**流式**比较（数据盘 512 MiB 不能整读）；数据盘跳过 MKFS 活动区 |
| `tools/rebuild_headless.sh` | 支持第二个参数 `NEX_MODEL_LAZY` |

### 宿主侧不再写 400 MB

模型打包是**独立的一次性步骤**（`make model-pack`），而且在**宿主本地盘**上跑，
不经过 VirtualBox 共享文件夹。内核构建只写 30 MB。
这直接消除了「每次构建写 400 MB 把构建 VM 写挂、SSH 握手超时、必须硬断电重启」
的老问题。

## 6. 过程中挖出的四个真实缺陷

### 缺陷 1：描述符结构体比一个扇区大 8 字节

初版 `ModelDescV2` 的 `reserved[432]` 让结构体变成 **520 字节**，而描述符只占
**512 字节**。后果：

* 宿主工具把 520 字节写进一个扇区 → payload 起点整体后移 8 字节；
* 内核 `memcpy_(&v2, sec, sizeof(v2))` 从 512 字节的栈缓冲区里读 520 字节
  → **栈越界读**。

修法：`reserved[424]`，`sizeof == 512 == 一个扇区`，宿主与内核用同一个常量
`MODEL_DESC_SIZE` 约束。

### 缺陷 2：手写 VDI 容器根本不是 VirtualBox 的 VDI

`tools/make_data_vdi.py` 沿用的是**经典 qemu VDI 1.1 布局**（字段从 0x40 起紧排）。
但 VirtualBox 自己写的是**另一种布局**：

| 字段 | qemu 布局 | VirtualBox 布局 |
|---|---|---|
| header size | 512 | **400 (0x190)** |
| comment | 0x54 (4 字节长度) | **0x54..0x153 (256 字节)** |
| offBlocks | 0x58 | **0x154** |
| offData | 0x5C | **0x158** |
| disk size | 0x70 | **0x170** |
| 头部文本 | `<<< innotek ... >>>` | `<<< Oracle ... >>>` |

所以手写的容器 **VirtualBox 打不开**。

### 缺陷 3：`vbox_check.py` 的数据盘校验一直是**空比较**

`vbox_check.py` 用 0x170 读磁盘容量，而旧 `data.vdi` 是按缺陷 2 的布局写的，
该处为 0 → 解析出的 payload 长度为 0 → **比较了两个空东西，永远报 "IN SYNC"**。

也就是说：数据盘从来没有被真正校验过，"IN SYNC" 这句话一直在骗人。
修法：源改用**裸镜像**，比较逻辑改成流式（1 MiB 分块），并对数据盘的
MKFS 活动区（900–16116）按设计跳过。

### 缺陷 4：`vbox_check.py` 会把「客人正常写盘」误报成 stale

数据盘的 MKFS 区是**活动文件系统**：每次启动 guest 都会往里写会话、快捷方式、
保存的文件。原逻辑把整个盘逐字节比对这些扇区，于是**第一次启动之后就永远
STALE**。现在按扇区区间跳过，并在报告里注明跳过了多少个扇区。
