# 商业白皮书 · 技术可行性备注（附录）

> 配套文档：NexOS 商业架构与生态定价白皮书 v1.0
> 本文的作用是**把愿景与已实现机制分开**，避免对外沟通时把蓝图讲成既成事实。
> 维护：ai-engineer · 状态：草案

## 1. 术语修正：Ring -4

**问题**：x86 特权级只有 Ring 0–3，不存在 Ring -4。比内核更低的隔离层是 hypervisor（VT-x / AMD-V）或 SMM，不是环。

**修正后的对外统一口径**：

- 现阶段 Ring -4 = **基于 MCP 总线 + 虚拟文件系统的强隔离沙盒**，不依赖 SVM/VT-x。它保证：应用只能通过 MCP 声明的工具访问被授权资源，身份由内核记录的 .mex basename 决定，managed code 无法自证身份。
- **SVM 硬件隔离是未来的安全扩展层**。当前状态：VMCB 被 QEMU 拒绝（#VMFAILVALID 根因未定，怀疑把旧的 host RFLAGS 误读成信号）。根因定位前，不得对外承诺硬件级隔离。

**现状对照**：

| 能力 | 状态 |
| --- | --- |
| MCP resident-set ACL | 已实现（nexos_ai.cpp） |
| SVM 虚拟机监控器 | 开发中，未通过 |
| 硬件级内存隔离 | 无 |

## 2. 双签机制：改为可选可信层

**问题**：强制双签要求 bootloader 内置市场 CA 公钥，信任根因此中心化，与去中心化矛盾；且会阻止任何自编译内核启动，直接摧毁可复现构建的验证路径（任何人能构建同一二进制，却引导不了它）。

**决定**：双签不做唯一入口，做**可选的可信层**。

- 默认：自签名 / 无签名镜像**可以启动**，进入开发者模式（红色警告）。
- 商业：通过双签的镜像获得 Verified by NexOS 绿色认证，才可在市场上架推广。
- 详见 docs/双签信任模型草案.md。

## 3. sys_install_derivative()：复用既有身份，不自造验签

**问题**：syscall 里看不到调用者签名。身份只能来自内核自己维护的凭证。

**决定**：复用现有 MCP 机制 —— g_current_app_id（CLR 实际加载的 .mex basename）+ app_registry_note_resident() 信任集。只有信任集内的系统级 .mex 可以调用。详见 docs/sys_install_derivative-接口草案.md。

## 4. A/B 分区与回滚：先逻辑备份 + 软件看门狗

**问题**：

- 镜像 SFS 槽位只剩约 **435 KiB**（构建期有 GUARD 会直接失败），物理 A/B 放不下。
- QEMU/TCG 没有真硬件看门狗。
- 5 秒内无 Boot Success 就回滚对 1 vCPU、TCG 约 12fps 的系统太紧，正常启动都可能误判。

**决定（分阶段）**：

1. **阶段一（现在）**：逻辑备份，把旧内核写入 SFS 保留目录或 data 盘；回滚由**软件看门狗**（内核定时器）驱动；判定信号改为 shell.mex ready（CLR 加载完成），超时放宽到 15–20 秒。
2. **阶段二（存储扩容后）**：真物理 A/B 分区 + 硬件看门狗。

**约束**：任何新增分区/镜像内容前必须先看 kernel.bin 与 SFS 槽位余量；当前 32 位镜像余量仅约 **350 B**。

## 5. 财务模型：标注为理想预估

- 50 万活跃用户 → 7.5 亿 GMV 等于人均年消费 1500 元，与无强制订阅、免费模板永远免费、不收广告费不能同时成立；原推算把企业客单价摊到了 C 端用户身上。
- 1 万用户时年抽成约 1 万元，不足以覆盖服务器 + CDN + 签名认证 + 安全审计；早期应标注为**投入期**，而不是勉强覆盖。

## 6. AI 线与按 Token 计费的落差

**现状**：AI 通道是 OpenCode 免费额度（匿名、无账号）+ 可选 DeepSeek Key，**没有配额账本、没有用量计量、没有支付回调、没有退款策略**。

因此按 Token 计费属于**远期规划**。当前优先级：

1. 本地 MCP 调度与本地推理（gguf_infer / ai_engine）可用；
2. 系统网络打通（当前 NIC 状态 DOWN）；
3. 计费/配额/账单等云端团队成立后再议。
