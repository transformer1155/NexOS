## 退出 GUI 黑屏修复 + 会话保存/恢复（用户实测反馈二轮）✅

### Bug 3：退出 GUI 后"黑屏"（ESC/终端图标退出后看不到终端）
- **实测定位**（screendump 分析）：退出后屏幕并非全黑——终端文本区（640x400 居中）有内容，
  但四周全黑（终端黑底）+ **文本颜色粉红** → 观感"黑屏"。
- **根因 A（颜色粉红）**：`fb_console_render()` 的 16bpp 分支
  `((color >> 10) << 5)` **没掩码**，R 通道低位污染 G 通道 → 所有文本粉红。
  修复：`(color >> 19) & 0x1F` / `(color >> 10) & 0x3F` / `(color >> 3) & 0x1F`
  （与 `present()` 的 16bpp 分支一致）。
- **根因 B（切回 VGA 文本模式）**：`gui_exit()` 里 `disable_vbe_mode()` + `vga_set_text_mode()`
  + `VGA_MEMORY=0xB8000` —— BGA 禁用后 QEMU 显示 0xB8000，而 term 渲染走 fbcon（VGA_SHADOW
  → LFB）→ 屏幕黑。**修复**：退出时保持 BGA + fbcon（`fb_console_render()` 直接渲染终端到
  LFB），不再切 VGA 文本模式。串口日志变 `[GUI] Exited GUI mode, fbcon text mode`。

### 功能：GUI 会话保存/恢复（"退出保存 → 重启 → 进终端 → 恢复"）
- **gui_exit() 自动保存**：`gui_session_save()` 遍历 `windows[]`，序列化可见窗口
  {launch_kind, x, y, w, h}（magic 'S' + count + 每窗口 9B）→ 写 MKFS 数据盘 `session` 文件。
- **gui 进入自动恢复**：`enter_gui()` 调 `gui_session_restore()`（g_startup_app_id 分支后），
  `launch_app(kind)` 重开窗口并恢复位置（跳过 APP_TERMINAL——它设计为退出 GUI）。
- **存储**：GuiCallbacks 新增 `session_save/load/clear`（kernel.cpp 用 `mkfs.create/read/remove`）；
  `session` shell 命令显示/`session clear` 清除。
- **注意**：`term.write` 不写串口（只写 VGA/fbcon），无头测试验证 `[SESS] saved/restored N`
  是 `serial_puts`（写串口）的日志。

### 附带修复：单盘 mkfs 破坏磁盘内核（严重既有 bug）
- **根因**：`MKFS_SUPER_LBA=512` 落在 kernel32.bin（LBA 3~804）范围内。单盘（os.img）下
  `fs_detect_data_disk` 把 primary master（系统盘）当数据盘 → `mkfs` 写 LBA 512-799
  **覆盖磁盘上的内核文件** → 重启后无法启动！
- **修复**：MKFS 区域移到安全间隙 `MKFS_SUPER_LBA=900 / TABLE=901 / DATA=917`（内核32
  3-804 之后、kernel64 2048 之前）。重启后系统盘完好，数据盘数据（session 等）保留。

### 关键认知修正（SFS 容量）
- 之前以为 `sfs_gen.py` 里 `total_sectors=207` 是硬上限（~103KiB）会装不下 dnSpy(207KiB)。
  **实测错误**：`sfs_gen.py` 按真实文件大小写 `sb+dir+file_data`，superblock 的 `total_sectors`
  只是元数据；内核按目录项里的 `start_lba` 直接 `ata_read_sector` 读，**不受 207 约束**
  （dnSpy 在 LBA 818 远超 207 仍被找到）。所以 SFS 实际容量≈磁盘剩余空间，不是 207 扇区。

  已接近上限，更大文件会越界）。

### 给用户结论
dnSpy.exe（以及任何 64 位 PE32+ 程序）**无法在 MiniOS 运行**：Win32 子系统只执行 32 位 i386 原生
PE32，且 MiniOS 没有 .NET/CLR 运行时（dnSpy 是 .NET/WPF 应用，即便 32 位也需要完整 .NET Framework+WPF）。
能存进 SFS ≠ 能执行。

## 64 位 PE32+ 真执行加载器 (Task #159, 完成于 2026-08-08 续)

### 目标与结论
- 用户要求"兼容 Win64 / 完整执行"。已实现 **真·64 位访客执行**：`winapp <x64.exe>` 经 `cmd_winapp`(kernel64.cpp) → `win32_ensure_init` → `win64_run`(win32.cpp)，把 PE32+ 映射进内核空间后 `int rc = fn();` 跑在内核 ring-0（ms_abi 调用约定，`WINAPI` 在 `__x86_64__` 下为 `__attribute__((ms_abi))`）。
- dnSpy（原生 x64 启动器，无 CLR 目录）在 64 位内核下 machine 检查已不适用 → 改由 **192 KiB 上限** 准确拒绝（`-6` "Image too large for the loader (192 KiB limit)."），内核不崩。

### 关键实现点
- `MAXPE = 192*1024`；`g_reader` 钳到该大小，故 `truncated = (fsz >= MAXPE)` 时必须拒绝，否则残缺镜像被当完整零填充 → 真实正确性问题（dnSpy 207KB 会触发）。
- PE32+ 规范：machine 0x8664 / magic 0x20B；ILT/IAT 为 8 字节 ULONGLONG 数组，**必须 NUL 终止**；按名导入时 thunk 为 IMAGE_IMPORT_BY_NAME 的 RVA，**bit 63 必须清零**（置位=按序号）。
- MS x64 ABI：调用点需 `sub rsp,40`（32B home space + 重新 16 字节对齐），返回前 `add rsp,40`；访客退出用 `ret`（绝不用 `hlt`）。
- DIR64 重定位自检：访客读 `reloc_probe` 运行期 VA 与经加载器修正后的存储值相减，结果为 0 即证明 delta 正确（`rc=0000000000000000`）。

### 测试车辆与坑 (tools/mk_hello64.py → sfs_files/hello64.exe, 1260B)
- 三坑已修：① ILT/IAT thunk 误 OR `1<<63` ORDINAL 标志位；② ILT/IAT 缺 8 字节零终止符 + 名字缺 `align(2)`；③ 代码段缺影子空间 + 尾部 `hlt` 而非 `ret`。
- `tools/test_win64.py`（TCP 串口）12 项断言全 `[ok]`，含 `dnspy_refused` / `dnspy_no_crash` → `RESULT: PASS`。
