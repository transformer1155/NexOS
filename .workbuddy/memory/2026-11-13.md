## OS API 升级线：L2 Process / L3 Glob 实机验证 + 64 位内核三重故障回归修复

- **环境坑（与代码无关）**：VBox 启动 NexOS 报 `VERR_UNRESOLVED_ERROR` / `E_FAIL ConsoleWrap`，VBox.log 里是 `Unhandled error 1455` + `pgmR3PhysInitAndLinkRamRange failed` —— 宿主提交内存 29.2/31.7 GB，装不下 4 GB 客户机 RAM。把 NexOS `modifyvm --memory 512/1024 --vram 32 --accelerate3d off` 后解决。强杀残留 VBoxHeadless 会在 VBoxSVC 留陈旧会话锁（`RPC_S_SERVER_UNAVAILABLE` / "already locked for a session"），需重启 VBoxSVC（Stop-Process 后自动拉起）才清得掉。Linux 构建 VM 曾被拖到 SSH banner 超时，硬断电重启后约 90s 才恢复。
- **64 位内核启动三重故障（D4/IST 层引入的回归，三个叠加 bug，已全修）**：串口停在 `[DIAG] step=1 kmain64 post-build_idt`，VBox Guru Meditation `VINF_EM_TRIPLE_FAULT`，VM-exit history = `#GP errcd=0x28` → `#PF` → `#DF`。用 Python 解析 `build/kernel64.elf` 符号表 + 反汇编 RIP 定位到 `kmain64+0x164` 的 `0f 00 d8` (`ltr ax`)。
  1. **主因**：崩溃时 `gdtr=0x11048:0x17`，即 CPU 仍用 32 位引导器的 3 项 GDT，selector 0x28 直接越界 → `ltr` 必然 #GP。旧镜像没有 `ltr` 所以从没暴露。修：`.attic64/kernel64.cpp::fault_ist_setup()` 里从 `gdt64`/`gdt64_end` 符号构造 `Gdtr64` 并显式 `lgdt`，再装 TSS 描述符。
  2. `gdt_install_tss()` 把 access byte `0x89` 写到描述符 **+7**（那是 base[31:24]），架构要求 **+5**；CPU 读到 P=0 → 描述符无效。修：`d[5]=0x89`、`d[7]=base>>24`。
  3. `entry64.asm` 的 TSS 用 8 字节 `dq 0` 开头（比架构的 `dd 0` 多 4 字节），CPU 读 IST1 在 offset **36**，代码却写 40；且栈指针指向数组首地址（压栈会向下踩 .bss）。修：写 `gdt64_tss+36`，值 `g_fault_stack+1024`（栈顶，0x39A700）。
- **修复后实机串口全绿**：`[K64-IDT] IST1 fault stack at 0039A700` → `[K64-COMPAT] armed` → SFS/ELF64/GGUF 模型加载 → `[OSAPI] layer0+1 armed abi=v1 htab=512` / `self-test fails=0` / `l2l3 self-test fails=0` / `[SHELL] osapi l0l1 ok=1 abi=1` / `[SHELL] osapi proc glob ok=1` / `[DIAG] step=332 mforms_start OK`。
- **Glob 自测假绿 → 真失败（已修）**：第二次 `proc/glob self-test` 报 `glob *.txt missed created file` `fails=1`。根因两条：① 自测经 icall 调用，`clr_new_str()` 在 CLR 上下文外返回 0，整段 glob 断言被 `if (ga[0] && ga[1])` 跳过 → 第一次 `fails=0` 是假绿；② 真正跑到时匹配条件 `q-p == 8` 与文件名 `globt1.txt`(9) 永不相符。修：`osapi.cpp` 抽出不依赖 CLR 的 C 侧 `osapi_fs_glob_c(dir,pat,out,outsz)`（返回字节数或 -1 BADARG/-2 PERMDENIED/-3 IO），icall 只做 `clr_new_str` 包装且失败补 `set_last_error`；自测直接调 C 函数，先 `remove` 再不带 `O_EXCL` 创建以保证幂等，按 `globt1` 前缀匹配。
- **构建工具**：新增 `tools/rebuild_k64.sh`（VM 内 touch 源 + 删 `.o`/`.elf`/`.bin` + `setsid` 后台 `make build/os_v2.img MODEL_GGUF=...` 写 `build/build_out.txt`）。共享文件夹 mtime 粗粒度，不显式删对象会链进旧 `.o`。每次增量含 400MB 镜像 dd，约 6–8 分钟。
- **Glob 失效的真正根因（ABI 语义错配，已修）**：`.attic64/kernel64.cpp::gui_cb_list_files()` 返回的是**条目数 `count`**（末尾 `return count;`，`pos` 才是写入字节数），而 `osapi_fs_glob_c` 把返回值当**字节长度**用 `while (i < n && list[i])`，只扫了缓冲区开头几个字节 → 永远看不到第一条之后的文件（含自测刚建的 `globt1.txt`）。修：`list[0]=0` 后扫到 NUL 结束符（带 `sizeof(list)-1` 上界）。`osapi_ic_dir_open/next` 那处只用 `n<0` 判错、按 NUL 扫描，本来就是对的。教训：跨层复用回调必须核对返回值单位。
- **最终实机串口（VBox NexOS，2026-11-13 13:2x，镜像 `MAKE_EXIT=0` / `k64 undefined: 0 (clean)` / VDI IN SYNC）**：`[K64-IDT] IST1 fault stack at 0039A700` → `[K64-COMPAT] armed` → `[OSAPI] layer0+1 armed: abi=v1 htab=512` → `self-test fails=0` → `l2l3 self-test fails=0` → `proc/glob self-test fails=0`（两次，均真实执行）→ `[SHELL] osapi l0l1 ok=1 abi=1` / `osapi proc glob ok=1` → `[DIAG] step=332 mforms_start OK`。无三重故障、无 panic。
