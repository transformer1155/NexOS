## 关键架构发现（非常重要）
- `os.img` 默认引导 **64 位内核**（`[K64] Entering Win11 GUI mode`、`[VMM] Long mode`）。64 位 gui.cpp 因 `NexOS_HAVE_MFORMS=0`，`gui_enter()`（gui.cpp:6531）只调用空桩 `mforms_boot()`，**不会加载 C# 托管壳**。
- C# 托管桌面（底部任务栏 / 壁纸 / AI 聊天 / 切换）只在 **32 位内核**路径加载：32 位 `gui_enter`（gui.cpp:6273）调用 `mforms_start()` → `clr_load("shell.mex")` + `Shell::Init`，成功后打 `[MFORMS] managed shell ready`。
- **登录门控**：串行日志 `[K32]/[K64] sign-in deferred to the graphical lock screen` —— C# 桌面要在**登录后**才激活。无头 QEMU 不登录，只能停在原生锁屏桌面（有顶栏 `draw_topbar`、有壁纸，**无底部任务栏**），故永远看不到 `[MFORMS]`/`[TB]`，也截不到 C# 桌面。
- 原生（64 位）桌面按设计**只有顶栏、无底栏**（gui.cpp 文件头注释 "Top status bar... not bottom"）。底部任务栏是 C# `Desktop.Taskbar()` 的特性。
- 结论：用户描述的"缺壁纸"只可能发生在 C# AI 桌面（原生桌面本来就有壁纸），所以用户实际就在 C# 桌面上；无头截不到是因为登录门控 + 64 位引导。

## AI 推理优化（目标：Ollama 级）— 勘察结论
- 用户要求把本地 AI 推理优化到 "Ollama 级别"（GGUF 量化、流畅跑 7B、流式、低延迟高吞吐）。
- **真推理在 64 位内核 `gguf_infer.cpp`**（`qwen_load/forward/generate/sample/tokenize`）；32 位 `ai_engine.cpp` 只是 Markov+玩具 mini-GPT（不参与真推理）。
- 已具备 Ollama 同款骨架：GGUF 解析、Q4_K/Q8_0 等量化 on-the-fly 反量化 matmul、RoPE/RMSNorm/attention、KV cache、流式、greedy/top-p/temp、GPT-2 BPE 分词。
- **核心瓶颈**：① 纯标量无 SIMD（`dot_q*` 全标量循环，Makefile 无 `-mavx2`）；② 单核无并行（OS 无抢占调度器，无 openmp/pthread 真并行）；③ 无 GPU/Vulkan/AMX；④ **无 chat template**（prompt 原样 tokenize，无 system/user/assistant 包装）；⑤ 模型被 4GB arena(`0xF0000000`)+QEMU `-m 4096` 封顶，实际 ≈1.7B、已验证 0.5B，7B 装不下；⑥ 单模型、无 mmap；Q2_K/Q3_K/Q8_K 解析了但 `type_supported()` 不让加载。
- **合理优先级**：① AVX2/FMA matmul → ② 多核并行 → ③ chat template+采样 → ④ mmap/撑 7B → ⑤ 量化补全 → ⑥ Vulkan/AMX。
- **验证约束（重要）**：SIMD/多核/大模型在 QEMU(TCG) 下可能不显效或无法验证，需在真机（Iris Xe i5）才有提速；chat template/采样增强可在 QEMU 直接看质量。AVX2 还需确认内核已置 CR4.OSXSAVE+XCR0（否则 AVX 指令 #UD）。
- **用户关键决策（2026-08-16）**：不要从零手写向量化，而是「去参考 Ollama 源码，看它如何处理 llama.cpp 的构建和调用」。已据此完成调研，报告落地 `docs/ollama-llamacpp-集成研究.md`。核心结论：Ollama = vendored llama.cpp 子模块 + CMake 多后端(`-DGGML_CUDA/METAL/VULKAN/HIP/SYCL/BLAS`，CPU 自动检测 AVX/AVX2/AVX512) + runner 子进程隔离(CGO 桥 `llama/llama.go`→llama.cpp C API) + chat template 由 `llama_chat_template_*` 应用 GGUF 内嵌 Jinja；CPU 速度秘诀是 ggml-cpu **运行时 SIMD 派发**(多套 AVX/AVX2/AVX512 核按 CPUID 选)。NexOS freestanding，不能直接用二进制；推荐路线 A = 把 ggml-cpu+GGUF+chat template 移植适配进 64 位内核，阶段：①GGUF 对齐 ②ggml-cpu 量化核+AVX2 派发(替标量 dot_q*) ③chat template(修 gap#4, QEMU 可验) ④malloc/mmap 适配 ⑤runner 隔离思想。后续让用户确认走路线 A 并从哪阶段起。

- **解决：手搓 gnu-efi-free UEFI 加载器**（不依赖 gnu-efi，用 x86_64-elf 交叉链 `-mabi=ms` + 自写 ELF→PE32+ 转换器）：

  - 内核嵌入方式复刻原流程：`cp kernel.bin kernel.blob; ld -r -b binary` → 符号 `_binary_build_kernel_blob_start`（注意原生 Windows ld 用绝对路径当符号名，须 `objcopy --redefine-sym` 改回规范名）；`enter_kernel.S` 纯 RIP 相对 asm，原样复用。
- **elf2efi.py 踩的坑（已修，全在工具里）**：① COFF 偏移算错（PE sig 在 0x80 后 COFF 应 0x84，差 4 字节导致 Machine=0 全错乱）；② EntryRVA=0（`_start` 虚拟地址 0 被"==0 即未找到"误杀 + `-shared` 下 `ld -e` 不写 e_entry，须靠 `.symtab` 回退并允许 0）；③ RVA 须整体加 `RVA_BASE=0x1000` 偏移（链接脚本 `.text` 在 VA 0，会与 PE 头重叠）；④ 本机 objcopy 无 PE 目标 → 改用自写 Python 出 PE；⑤ 必须加合法 `.reloc` 终止块（PageRVA=0,BlockSize=0）并**清 RELOCS_STRIPPED 位**，否则 OVMF 因"无重定位不在首选基址"直接拒载（`Script Error Status: Unsupported`）。
- **验证结果**：

### EFI 黑屏根因突破（2026-08-16 深夜，最新）
- **关键反转**：先前"EGI3SFB 后 [K1]/'Z' 零输出"是**假象**——`kmain` 首行的裸 `outb` 内联汇编写成了 `movb $0x5A, %al` / `outb %al, %dx`，GCC 把 `%` 当操作数引用而**编译报错**（`invalid 'asm': operand number missing after %-letter`），那段内核根本没编过，QEMU 跑的是更旧的 kernel.bin。修正为 `%%al`/`%%dx` 后 'Z' 与 `[K0]` 立即出现。
- **实测真相（无头 QEMU + serial 抓帧）**：kmain **确实进入了**（'Z' 裸 outb + `[K0] kmain entered, PIC masked` 都打出来），但紧接着 `gdt_init()` 里 **`ltr 0x28` 加载 TSS 三重错误→复位→重新 EFI→再循环**（`EGI3SFBZ[K0][G.l][G.t]` 反复出现）。在 gdt_init 的 `lgdt`/`ltr` 前后加标记确认：`[G.l]`/`[G.t]` 各出现多次，**[G.d]（ltr 之后）恒为 0** → `ltr` 即崩溃点。
- **根因**：UEFI 路径下 CPU **一直处于长模式**（IA-32e，enter_kernel.S 留 32 位兼容子模式，UEFI 4 级页表不退出）。`gdt_init()`（`gdt.cpp:54`）用的是 **8 字节 32 位 TSS 描述符**（`access=0x89`，`GdtEntry` 8 字节）。长模式下 `ltr` 要求 **16 字节 64 位 TSS 描述符**（type 9 + 描述符 16 字节，基址高 32 位在上半部）。8 字节描述符被当 16 字节读，把相邻的 `g_gdtr` 当描述符高位 → TSS 基址变成 >4GB 非规范地址 → `#GP` → 三重错误。BIOS（纯 32 位保护模式）路径下 8 字节 32 位 TSS 正常，所以只在 EFI 路径崩。
- **影响判定**：这是 EFI 路径黑屏的**第一道**阻断（比 >4GB 帧缓冲更早）。即便修了 `vmm_check_long_mode`（EAX bit10 LMA），`gdt_init` 也会先崩，GUI 永远到不了初始化。真机黑屏大概率同因。EFI 路径要让 GUI 出来，必须：① `gdt_init` 在长模式下用 16 字节 64 位 TSS 描述符 + 64 位 TSS 结构（或长模式路径跳过 TSS 加载）；② 很可能 `idt_init` 也有同样的长模式 16 字节门描述符问题，需要一并处理。
- **验证流程新增坑（必记）**：
