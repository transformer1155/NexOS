## 内核边界扩容（应用级多进程，已实测）
- 用户口径确认：**不做 OS 级页表/调度器**（当前系统没有真多进程：`proc.h` 明写 scheduler is later、`syscall.h` 只有 8 个调用、`proc_isolation.cpp` 刻意未链接），而是扩 **MiniCLR 槽 + 窗口** 这一层，让多个 .mex 应用/多窗口各自独立映像。
- **关键事实（解决旧疑问）**：桌面 GUI 与 MiniCLR 槽实际跑在 **64 位内核**（serial `[K64] Entering Win11 GUI mode`），堆是 `.attic64/kernel64.cpp` 的 **16 MiB**，不是 32 位的 128 MiB。每槽约 840 KiB → `CLR_MAX_VMS=8` 上限安全（~6.7 MiB），16 槽会占 88% 不可行。
- 改动文件：新增 `app_registry.h`（单一真源：AppType/Kind/mex 名/容量常量/独立 handle 段 64+）、`clr.h`+`clr.cpp`（`CLR_MAX_VMS` 4→8 移到头文件、新增只读 `clr_slot_loaded()`）、`mforms.cpp`（修重复 `MFORMS_MAX_WIN` 16/32、注册表取代 `app==7`、动态 handle+槽分配、`mforms_close` 首次真正调用 `clr_close_slot`、Title/Pan 按槽分派、`clr_use` 返回值检查、启动自检释放槽 1）、`src/gui/gui_legacy.cpp`（`MAX_WINDOWS` 12→16、删除重复绑定、失败回退改 `managed_kind_for(app)`）、`Makefile`（`app_registry.h` 加入 32/64 位 mforms 规则依赖）。
- **坑**：`MAX_WINDOWS=24` 会撑爆 32 位 `.bss` —— `linker.ld:105` ASSERT `__bss_end <= 0x9C0000`，实测真实 `__bss_end` 已 0x9A6098（余 ~106 KiB）。**窗口表上限只能 16**，并发上限由槽数决定。`app_registry.h: NEX_APP_MAX_WINDOWS` 与 `gui_legacy.cpp: MAX_WINDOWS` 需人工同步。
- **构建/验证**：`vm-run make` 全绿（k64 undefined = 0 clean，`build/os_v2.img` 31 MB）；验证脚本 `build/verify_standalone.py`（QEMU `-m 512 -accel tcg -snapshot`，等 `[GUI] Entered GUI mode` 后**不要注入按键**，镜像自动进 GUI，按键会被桌面吃掉；直接 `mouse_move/mouse_button` 双击 (64,64) 图标）。成功标记：`[gui] opening standalone app 11` → `[CLR] loaded Notepad.mex` → `[MFORMS] standalone app live in slot 1 handle 64`，无 paint/Init 故障。
