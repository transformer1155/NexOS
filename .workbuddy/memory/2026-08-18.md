## 64 位内核诊断基础设施（串口+落盘）落地并验证

### 背景
延续"真机 64 位 UEFI GUI 黑屏冻结"诊断：用户诉求"不看颜色直接把日志存盘"。
选型"串口+落盘双写"。本机只能重建/验证 BIOS raw 路径（os.img）；UEFI 路径
kernel64 编进 BOOTX64.EFI blob，本机无 host gcc 无法重建。

### 修复：IDT gate 绝对地址重定位（build_idt）
- 根因：64 位内核 ELF 链接基址 0x100000，但 32 位加载器 kmalloc 把
  kernel64.bin 暂存到可变物理地址（BIOS 路径实测 0x300010）。IDT gate 目标是
  绝对地址，若直接用链接基址填 gate → 装 IDT 即 triple fault → 静默重启。
- 中间踩坑：先试 `call 1f; pop %0` 取址，因 `pop` 落在 `call` 之后 5 字节，
  delta 算成"链接基址+5"→ off-by-5，仍错。最终用 `lea 0(%rip), %0` 取
  `idt_self:` 运行地址，减 `&&idt_self`（链接地址），delta 精确。
- BIOS 路径实测 `[K64-IDT] delta=0000000000000007`，正确。装 IDT 后不再
  triple-fault 重启循环。

### 新增诊断设施（.attic64/kernel64.cpp）
- 256 项 IDT stub（entry64.asm）+ isr_common + fault_common（串口打印
  vec/err/rip/cr2/step 后 cli;hlt）+ diag_step（串口打印+记录最后步）。
- kmain64：build_idt() + diag_step(1)/(2) 早期标记；gui/mforms 全量插
  diag_step（100–333，见 diag_step_legend.txt）。
- 32 位 kernel.cpp 留 diag_step 空实现；gui.cpp/mforms.cpp 的 boot_beacon
  调用改为 diag_step。

### 关键发现：64 位早期写盘会冻结内核（与真机黑屏可能同源）
- 实测：diag_step 在 kmain64 早期（build_idt 后、boot_beacon 前）调用
  ata_write_sector 写盘 → 内核在 boot_beacon 处**硬冻结**（串口停在 step=1，
  kmain64 只进 1 次、无恢复、无 [DIAG-FAULT]）。原 triple-fault 可恢复重启
  路径一旦早期写盘就变不可恢复硬挂死。
- 机理疑为 64 位长模式 ATA PIO 写盘对早期启动状态（显示初始化读盘/页表窗口）
  的副作用，具体待查。这是真实 64 位早期启动稳定性 bug，建议作为"真机黑屏"
  候选根因单独排查。
- 规避：diag_step 落盘只覆盖步号≥100 的后期阶段（跳过 300–311 重绘噪声），
  早期 1/2 步仅留串口。fault_common 仍对所有故障落盘。

## 根因：64 位 UEFI 下 gfx.lfb 取自错误/被截断的 FB_VIRT
- 华为真机报告：里程碑探针最终屏 = 青色（GU-B），无白角 → enter_gui 内挂。
- 代码分析：enter_gui() -> gfx.force_clear_lfb() 用 gfx.lfb；若 gfx.lfb==0 则
  直接 return（屏保持青色）；随后 render_all() 往地址 0 写 → #PF → freeze。
- gfx.lfb 由 gui_enter 从 addr_virt(ADDR_FB_VIRT) 取；若该值为 0（32 位物理
  截断）或指向 0xF0000000 兼容窗口（只在 32 位页表存在），就会在 64 位下 #PF。
  boot_beacon 用 0x5000 GOP 结构里的 64 位 FB 基址，华为已验证可达。
- 修复：gui_enter() 中优先使用 0x5000 GOP 的 framebuffer_phys64 作为 gfx.lfb，
  并同步 addr_set(ADDR_FB_VIRT, fbv, fbv, ...)。这是被 boot_beacon 证实的地址。
- 同时在 enter_gui() 里加 E1/E2/E3 子标记：橙(过 gfx 初始化)->浅蓝(enable_vbe后)
  ->深灰(force_clear_lfb后)->白角(enter_gui返回冻结)。用于真机验证 lfb 修复
  是否生效；若仍卡住，子标记能指出新位置。
- 重建 kernel64.bin(516144)+BOOTX64.EFI(2775048)+注入 os_uefi_diag_probe.img。

## 分布式算力网络最小原型（distnet）落地 + 两 VM 实测 PASS

### 目标与选型
- 从"真机 64 位 UEFI 黑屏"切到分布式算力网络赛道；选最小可用原型：
  mDNS 风格广播发现 + 周期性 QUERY 重发 + 简单任务分发/结果回收 loop，
  两台 guest（QEMU UDP socket 隧道）间验证。
- 端口规划：DN_BEACON_PORT=5355（信标发现）、DN_TASK_PORT=5356（任务下发）、
  DN_RESULT_PORT=5357（结果回收）；任务类型 sum/echo/compute。

### 改动文件
- `net.cpp`（仅依赖既有 API，未改）：NE2000 ISA 网卡（0x300）、`our_ip=10.0.2.15`、
  IP 按主机序大端可读（`IPV4(a,b,c,d)=a<<24|...`）；已有 `net_udp_send`/
  `net_udp_broadcast`/`net_udp_bind`/`net_log`/`net_set_ip`。关键机制：
  `handle_arp` 收到针对本机的 request 时 `arp_add+arp_reply`、收到 reply 时
  `arp_add`；`ip_send` 单播 ARP-miss 则 `arp_request` 后丢包。这就是 scheduler
  周期重发 QUERY 能让 compute 节点"首次借 QUERY 触发 ARP、下次 QUERY 成功回信标"的根因。
- `distnet.cpp`（核心）：scheduler 端由"单次 QUERY+单次等待"改为"周期性 QUERY 重发
  （QUERY_INTERVAL=20000 polls、QUERY_MAX=15），直到收到 BEACON 或放弃"；compute 端
  `distnet compute` 上线即周期 beacon，收到 TASK 调 `exec_task` 回 RESULT。
- `kernel.cpp`：接入 `distnet scheduler` / `distnet compute [target_ip]` / `setip`
  命令（*32 位专属*，不切 64 位、不重启）。
- `Makefile`：585–614 `textboot` 目标链 + 132–133 `distnet.o` 编译；186–187
  默认 `kernel.elf` 也已链入 `distnet.o`（即 `os.img` 默认镜像含 distnet）。

### 关键坑（勿再踩）
1. **freestanding -O2 字符串拼装会乱码**：在 `-O2 -ffreestanding` 下反复
   `result[my_strlen(result)]` 找末尾再写，实测产出 `RESULT 1 ok 1v5ðû` 乱码。
   → 全量改用索引维护的 `rcat(out,&rp,s)`（末尾手动写 0），乱码消除。
2. **64 位内核陈旧对象导致 textboot 链接失败**：`g_skip_enter_gui` undefined
   引用是 `build/kernel64.o` 陈旧所致（当前 `.attic64/kernel64.cpp` 已无此符号）。
   → 构建前 `rm -f build/*64.o build/kernel64.elf build/kernel64.bin` 干净重编。

## os.img 启动即"蓝屏闪退"根因（QEMU 表现为 64 位重启循环）

- 用户在自己的终端跑 `os.img` 报告"一看到蓝色就闪退"。抓串口（`-display none -serial file:`，
  跑 ~22s 后 kill 再读文件，文件缓冲在退出时刷出）确认：os.img 启动后
  32 位到 `Shell ready` → 自动切 64 位 → `[K64-1] kmain64 entered`/`[K64-IDT] installed`/
  `[DIAG] step=1 kmain64 post-build_idt` → **立刻 triple fault 重启** → 退回 32 位从头 boot，
  无限循环（22s 内 13 次）。
- "蓝色"= 每次循环里 boot / 刚进 64 位那一下的画面；"闪退"= 我给的命令带了 `-no-reboot`，
  把第一次重启变成 QEMU 立即退出 → 窗口消失。
- **这就是"真机 64 位 UEFI 黑屏/冻结"同一条 bug 在 QEMU 上的表现**：QEMU(tcg) 下 triple fault
  会重启（循环），真机可能直接卡死黑屏。崩溃点在 64 位 `kmain64` 的 `diag_step(1)` 之后、
  `diag_step(2)` 之前（即 build_idt 之后极早期），尚未定位具体指令。
- **稳定可用替代镜像**：`os_textboot.img`（纯 32 位、不切 64 位、不重启，distnet 验证用过，稳定）。
  给用户看系统用这个；`os.img` 在 64 位早期崩溃修好前不要直接跑（或去掉 `-no-reboot` 只看循环）。
- 后续：要真正修 os.img，需顺着 `diag_step(1)→(2)` 之间代码揪出 64 位早期崩溃点（见上面
  "64 位内核诊断基础设施"与">4GB 帧缓冲黑屏"两节，属未结真机黑屏线）。
