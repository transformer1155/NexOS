## 高帧缓冲黑屏根因最终修复（2026-08-17 晚间）
- **用户反馈**：真机仍黑屏、没进图形界面、报内存问题；QEMU 显示 98.76% 的 800×600 画面却无法解释真机。
- **根因①**：`kernel.cpp` 的 `vmm_map_high_fb()` 为 >4GB GOP FB 建的 4 级页表全部位于 `.bss`（`g_win_pt 0x128000` / `g_pd 0x148000` / `g_pdpt 0x14C000` / `g_pml4 0x14D000`），且被加载到 CR3。`switch32to64.asm` 的 `.compat_path` 原先把 kernel64 镜像 `rep movsd` 到 **0x100000..0x180000**，正好覆盖这些活动页表 → CPU 再次 walk 页表读到 kernel 字节 → **triple fault 无限重启**。FB <4GB 时不会触发 `vmm_map_high_fb()`，所以 QEMU 一直绿的。真机 FB 在 `0x4000000000` 必触发此路径。
- **修复①**：`.attic64/switch32to64.asm` 的 `.compat_path` 先安装 0x90000 页表并切 CR3，再执行 `rep movsd` 镜像拷贝。0x90000 页表区在 blit 窗口之外，且同样覆盖 0..8GiB（1GiB 大页）并附加 >4GB FB 映射。
- **根因②**：`vmm_map_high_fb()` 里的窗口页表按 **1024 项/页表**索引（32 位非 PAE 写法），但长模式只有 **512 项/页**。结果只正确映射了前 2 MiB 窗口；800×600×4 = 1.92 MiB 刚巧能跑，真机原生分辨率（1920×1080×4 = 8.3 MiB 起）一过 2 MiB 就 #PF，正好对应「满屏就黑」。
- **修复②**：改 `FB_WIN_PT_ENTRIES=512`、`FB_WIN_PTS=32`（64 MiB 窗口），索引用 `/ 512` 和 `% 512`，并加入越界保护。
- **验证（TEST_HIGH_FB）**：在 QEMU 用 fake FB 地址 `0x124000000`（等价 >4GB 映射数学）+ `-m 5G` 跑 `tools/qemu_highfb_test.py 50`：结果 `PASS`，`xp 0x124000000` 出现桌面像素 `0x005ABEEF`；调试字符序列从 `SU` 变成完整 `SUPHXCM6aefgbcd...`；启动横幅只出现 1 次，无重启循环。
- **回归（正常镜像）**：重建 `build/os_uefi_test.img`，`qemu_uefi_capture.py` 仍录得 **98.76% non-black (800×600)**。
- **新教训**：长模式页表项数是 512，不是 1024；CR3 指向的页表位置必须在后续写操作之前确认不在被写范围内；>4GB 路径必须用 fake 地址在 QEMU 强制复现，否则永远漏测。

## 真机「橙色停住」= GUI 启动期 #PF（2026-08-17 晚，最终根因）
- **用户回报真机最后常驻色 = 橙色**（stage8，`gui_enter()` 入口信标）。橙色能显示证明 `boot_beacon` 用的真实地址 `framebuffer_phys64` 在 64 位页表里**已正确映射**；但之后桌面永远不出现、且不灰屏（64 位 fault 只 hlt 不刷灰）。
- **根因（最终、确凿）**：`struct Graphics{ volatile uint32_t* lfb; }` 的 `lfb` 在 **32 位 `fb_console_init()` 里被 `Gfx::init()` 设为 `framebuffer_phys`**，而 `vmm_map_high_fb()` 已把 `framebuffer_phys` 改写成 **`0xF0000000` 的 32 位 shadow 窗口**。`Gfx::init()` 里的 `#if defined(__x86_64__)` 分支（`lfb = framebuffer_phys64`）**运行时从未执行**——`init()` 只在 32 位调用一次。于是 64 位下 `g_wm.gfx.lfb = 0xF0000000`，而 **64 位页表没映射 `0xF0000000` 窗口**（只映射了真实地址 `framebuffer_phys64`，由 `switch32to64.asm` 做恒等映射）。`enter_gui()` 的 `force_clear_lfb()`/`render_all()` 走 `lfb` → 写 `0xF0000000` → **#PF → 64 位 handler hlt → 冻在橙色**。这解释了「橙色能画（boot_beacon 直接读 framebuffer_phys64）、桌面画不出、QEMU 正常（FB<4GB 时 vmm_map_high_fb 是 no-op，lfb=真实地址且 64 位已映射）」。
- **修复（最终）**：在 `gui_enter()`（64 位上下文）里，`#if defined(__x86_64__)` 块把 `g_wm.gfx.lfb` 重新指向 `framebuffer_phys64`（仅当 `fb64 > 0xFFFFFFFFULL`）；QEMU（FB<4GB）跳过该块、行为不变。配套在 `mforms_boot()` 与 `enter_gui()` 内加了细粒度信标（PINK=纹理加载完 / VIOLET=host 表就位 / AZURE=托管壳启动 OK / DARK RED=托管壳失败 / MINT=enter_gui 进入 / PALE=enter_gui 返回），烧盘看最后色即可再定位。
- **验证**：重建 `build/os_uefi_test.img`（134205952 字节），**SHA256 `6571372823ec36138c995a6ecee98595d99d4931810aec0c4a380df8d750102c`**。`qemu_uefi_capture.py tcg 10 16` → **98.76% non-black (800×600) GUI VISIBLE**（lfb 修复对 QEMU 无副作用）。
- **预期**：真机烧此镜像应直接进入桌面（或至少过 MINT/PALE 出现原生壁纸）。若仍只橙色，则 beacons 会显示是卡在 `mforms_boot()` 的 CLR/托管壳启动（PINK/VIOLET/AZURE 哪一档），那时再单独修 CLR 路径。

## 新增地址管理注册表 `addrman`（2026-08-17 更晚）
- **需求**：用户在桌面问题解决后要求「在内存管理里面加地址管理」。按确认选择：命名地址注册表、新建独立模块 `addrman.cpp`/`addrman.h`。
