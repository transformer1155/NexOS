## 注入测试脚本 vm_inject_test.py (把本地 .exe/.zip/.bat/.com 带入系统测试)
- 新文件 `tools/vm_inject_test.py`：命令行传本地文件 -> 注入 SFS -> 重建镜像 -> 启动 VM -> 在系统里逐一 `run`/`runfs`/`catfs` 验证 -> 从串口日志给判定。
- SFS 是扁平 19 字符命名空间：脚本对注入名做 ASCII 化+长度截断(保留扩展名)+去重；`.zip` 解包并扁平化成员名。
- GUI 模式是模态的：一旦 `run xxx.exe` 进 GUI，文本 shell 不再读键盘，后续命令会被吞。故脚本自动分组——非 GUI 文件(.sh/.txt 用 catfs 校验)同一次启动跑；每个 .exe/.bat/.com 单独启动一次 VM，靠「加载器已接收」([GUI] Initializing on demand for:)判定。
- 判定语义：对注入测试而言『文件进了 SFS 且被交给加载器』即 PASS；非 PE 桩(.com 2字节)报 DISPATCHED 也算过，只有 File not found 才 FAIL。
- 清场：默认移除本次注入的文件并把 sfs.img/os.img 还原；新增保护——绝不删改运行前已存在的基础文件(如 hello32.exe)。--keep 可保留。
- 运行：`wsl -e bash -lc 'cd /mnt/d/MyOS/bootloader && python3 tools/vm_inject_test.py /tmp/a.bat /tmp/b.zip'`。Windows 路径经 wslpath 转换；绝对 POSIX 路径直接透传。

## 修复 framebuffer console 显示布局
- 问题：`make play` 在 1920x1080 VBE 窗口里只显示左上角 640x400 白块，其余黑屏。
- 根因 1：`gui.cpp` 的 `fb_console_render()` 只清 640x400 区域并渲染到 (0,0)。
- 根因 2：`VGA_MEMORY` 在 VBE 模式下仍指向 0xB8000；Bochs-VBE 对该端口读回 0xFF，导致属性字节被当成 0xFF（白底白字）。
- 修复：
  - `kernel.cpp` 进入 fb console 模式时：`VGA_MEMORY = VGA_SHADOW;` 并初始化 shadow 为黑底浅灰字。
  - `gui.cpp` 的 `fb_console_render()` 现在先清整个帧缓冲为黑，再把 80x25 终端居中绘制。
  - `gui.cpp` 的 `gui_exit()` 恢复 VGA text mode 时把 `VGA_MEMORY` 指回 0xB8000。
- 结果：登录界面现在是黑底、居中的正常终端；`make test-sec` 仍 PASS。


## mforms / C# GUI 修复：托管 About/TaskManager/MemOptimizer 等不再 #PF 崩溃
- 问题：计算器(PASS)能运行，但 About/TaskManager/Memory/Control/Files/Terminal 一运行就 `#PF page fault`，`EIP=1, CR2=0xFFFFFFEC`。
- 误诊与纠正：最初以为是 `-O2` 把 icall 包装函数优化成 `jmp *funcptr` 尾调用，加了 Makefile `-fno-optimize-sibling-calls`（保留）; objdump 确认确实变成 `call *0x311c`，但崩溃仍在。
- 真因：`kernel.cpp`(32 位) 里定义了 `register_gui_callbacks()`，但只在 `kernel64.cpp` 中调用，32 位路径从未调用它。导致 `gui.cpp` 的 `g_cb` 全零，所有机器状态回调（`get_total_mem_kb` 等）都是 NULL。`mforms_boot()` 把 NULL 拷进 `MFormsHost.g_h`，C# 调用 `Host.MemTotalKb()` 时 `call` 到地址 1，栈被打烂后 `#PF`。
- 修复：
  - `kernel.cpp` 在 `cmd_gui` 中 `gui_init()` 成功后加 `register_gui_callbacks()`；在 `cmd_gui` 前加前向声明。
  - Makefile 给 `mforms.cpp` 加 `-fno-optimize-sibling-calls`，并在源码里加注释说明函数指针间接调用的问题。
  - 清理 `csharp/apps/Shell/Apps.cs` 中 About.OnPaint 的调试 `Host.Log("ABOUT: ...")` 标记。
- 回归：`python3 -u tools/test_mforms.py about/tasks/memory/control/files/term/calc` 全部 PASS，截图确认 C# 应用正确渲染；`make test-sec` 仍然 PASS。

## 坑：WSLg 下 `make play` 报 Gdk Error 71 (Protocol error) dispatching to Wayland display
- 现象：`make play` 立刻退出，`make: *** [Makefile:465: play] Error 1`，QEMU 窗口根本没出来。
- 根因：WSLg 同时提供 Wayland (`WAYLAND_DISPLAY=wayland-0`) 和 X11 (`DISPLAY=:0`, `/tmp/.X11-unix/X0`)。
  GTK 默认优先选 Wayland，而 WSLg 的 Wayland compositor 会在握手中途断连 → Error 71。
  同一台机器上的 XWayland 是稳定的。
- 修复：`Makefile` 新增 `GUIENV := $(shell [ -d /mnt/wslg ] && echo GDK_BACKEND=x11 SDL_VIDEODRIVER=x11)`，
  并在 `run` / `bios-run` / `play` 的 qemu 命令前加 `$(GUIENV)`。原生 Linux 桌面下 `/mnt/wslg`
  不存在，GUIENV 为空，不影响默认行为。
- 另加两个后备目标：`make play-sdl`（`-display sdl`）、`make play-vnc`（`-display vnc=127.0.0.1:0`，
  用 VNC 客户端连 127.0.0.1:5900，适合完全无本地显示的场景）。
- 验证：`setsid timeout 14 make play` → 内核完整引导到 `[K5] Hello world written`，EXIT=124
  （被 timeout 正常掐断，说明持续运行），Wayland 报错消失。
- 自动化下测 GUI 目标的技巧：`setsid timeout N ... > log 2>&1 < /dev/null`，
  再读 log。直接跑会因 `-serial mon:stdio` 抢 stdin 而使 wsl 返回 exit 15。
