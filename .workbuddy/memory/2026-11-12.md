# 2026-11-12 NexOS 64 位内核 — VBox 模型加载跑通

## 修复：VBox BM-DMA 崩溃（用户「用 VBox 先跑通逻辑」）
- 根因：`.attic64/kernel64.cpp` 的 `ata_read_dma_block()` 把 `big_alloc()` 返回的 C 指针直接当**物理地址**写入 PRDT；379MB 模型缓冲落在高端且物理页不连续，Bus Master 写越界 → VirtualBoxVM.exe 内部断言断点 0x80000003 崩溃。串口日志 `[ATA] BM-DMA base=0000D000` 印证 VBox 上 BM-DMA 初始化成功、旧 `use_dma=(g_bm_base&&g_prdt_phys)` 为真会走此路径。
- 改动：`model_blob_read()` 内 `use_dma=false`（注释写明后续启用条件：buffer 须物理连续且落在 identity-map 窗口）。同时修了 PIO 分支 `batch>1` 丢数据遗留 bug——改逐扇区循环填充 `dst+done+j*512`（原代码只读 1 扇区却按 batch 前进）。
- BM-DMA 代码保留（现 unused，编译警告），待后续磁盘驱动兼容性任务真正修复。

## 2026-11-12 下午：两项遗留修复（用户「两个都修」）均已修 + VBox 验证通过
- **(A) 多扇区 PIO 在 VBox 卡死**：上一轮为提速引入 `ata_read_multi`(count>1) 作 PIO 快路，但在 VBox PIIX3 IDE 上 count>1 READ 使 BSY/DRQ 永不清除 → loader 永久 busy-spin（实测 ~80% CPU、零进度标记、永不完成）。根因非 BM-DMA（那个已禁用），而是多扇区命令本身。修法：`model_blob_read` PIO 分支改为**纯单扇区 `ata_read_sector` 循环**（即 SFS 同款，三平台可靠），带 1 次 soft-reset 重试、仍失败则 return 0 不自旋。BM-DMA 仍禁用（待物理连续 bounce buffer 根治）。
- **(B) 桌面 CLR 越界**：`csharp/apps/Shell/Desktop.cs` `const int KINDS=18` 与 `Kind` 枚举（`AiChat=18`，共 19 值）不符，`kName=new string[18]` 却写 `kName[18]` → 数组越界 → `mforms_start FAILED`。修法 `KINDS=19`（注释同步）。
- **VBox 无头验证（startvm --type headless，串口 `build/vbox_serial.log`）**：

## 2026-11-12 追加：修复 VirtualBox 满屏紫黑竖条纹（根因 + 内核自愈 + VDI 同步）
- **症状**：VBox 启动后满屏紫黑竖条纹。
- **根因三层**（前次笔记的「指针当物理地址」说法是错的，已纠正）：
  1. **VDI 陈旧**：`tools/vbox_check.py` 报 `os_v2_vbox.vdi STALE`，首个差异正好在 payload offset 512（LBA 1 = stage2 起点）→ VM 跑的是旧 stage2。
  2. **旧 stage2 从不写 0x500F（pixel_format）**，且在 VBox 上选中了 **16bpp** 模式 → 串口日志同时出现 `bpp=16 pitch=2048` 与 `fmt=0(BGRX32)`，位深与像素格式自相矛盾。

## 2026-11-13 盘点：Win32/PE 兼容层的内核边缘功能缺口（只读盘点，未写代码）
- **修正用户前提**：「32 位 kernel.bin 剩 350 B」是**过期信息**。kernel.bin 现在只是引导桩

  0x400000-0x100000=3 MiB，已用 1,114,256 → **余 ~2,031,472 B**。
  → 结论：**新代码放 kernel64 完全可行，350 B 约束不成立**；但 .bss 与代码窗口仍需精打细算。

- **PE 执行模型 = ring-0**：win32.cpp 的 PE32+/PE32 加载器把映像 kmalloc 到内核地址空间，

- **64 位 GDT 无 FS 描述符**：.attic64/entry64.asm 的 gdt64 只有 5 项（null/64code/64data/32compat code/32data），

- **导入策略是"全有或全无"**：任一导入符号缺失 → `return -5` 拒绝执行。w32_resolve 有第二遍
  "忽略 DLL 名"兜底，但表里没有的函数就是没有（当前 6 个 DLL：kernel32/user32/gdi32/advapi32/msvcrt/NexOS）。

## 2026-11-13 D 类盘点：AI 作为「外部翻译调度器」介入兼容层（只读盘点，未写代码）
- **目标形态**：AI **不在内核里做计算**，而是外围「看着 PE 跑，缺 API 或崩了 → 喂映射/兜底方案」。
  ⇒ D 类的第一性问题不是「怎么记录」，而是**外部 AI 凭什么通道跟内核说话**。
- **通道盘点（实测）**：
  - `run_command()` 是内核唯一命令入口（`kernel64.cpp:6200+` 的 if-else 链），只从 `term`/串口读。
  - `net_http_get()` 只有**出站** HTTP 客户端（net.cpp），**没有 inbound server/accept**。
  - **MKFS 数据盘是双向的**：`mkfs.read()` / `kern_fs_create()`（kernel64.cpp:6126）能读能写，
    且数据盘是 `build/data_vbox.vdi`（宿主机可挂载）→ **这是外部 AI 最现实的通道**：
    AI 在宿主机写 VDI 里的文件，内核每帧轮询读取。
  - 已有 `ai` / `ask` / `agent` 命令 + `kern_ai_ask()`（kernel64.cpp:9158，走本地 GGUF）。
- **D1 观测点**：
  - `w32_resolve()`（win32.cpp:2088）返回**函数指针**，被写进 IAT（`*(uint64_t*)(g_base+ft+k) = fn`）。
    → 天然的观测点是 **IAT 槽位**，不是 thunk 内部（thunk 是 111 个不同函数，逐个埋点成本高）。
  - 已有 APMS 事件环（`.attic64/apms.inc`，64 条 `ApmsEvent` + 8 KiB 串口 tee 环）可复用格式，
    但**是 managed 侧拉取**（`Host.ApmsEvent`），不能被外部 AI 直接读。
  - `fault_common()`（kernel64.cpp:935）已记录 vec/err/rip/cr2/step 并写 LBA1500，**但结尾是
    `cli; hlt` 永久停机** → 对 AI 调度场景**致命**：一次野指针就把机器钉死，AI 永远等不到。
- **D2 热补丁**：
  - IAT 在加载时写死，但**地址可重算**：`imp_rva`/`ft` 已知，`g_base` 全局 → 任何时刻都能
    `*(g_base + ft + k) = new_trampoline` 改写。**不需要重编译内核**。
  - `w32_resolve` 有「忽略 DLL 名」第二遍兜底 → 可用于反向查询（IAT 槽 → 原函数名）。
  - 现有 `W32Export{name, fn}` 表（win32.cpp:1885）是天然的「名字 → 实现」注册表，
    AI 提供新实现时应写入**同一张表的动态区**（现在是 `static const`，需改为可增长数组）。
- **D3 降级**：
  - 哑句柄可行：现有假句柄已是这个套路（`H_WRITE`=0x??、`0x00F5` 文件句柄、`0x00E0` 线程句柄）。
  - 缺句柄时 `SetLastError(ERROR_CALL_NOT_IMPLEMENTED=120)` + 返回哑值，是 Win32 允许的降级形态。
  - 但**导入阶段**现在是「全有或全无 → return -5 拒绝执行」；D3 要求改成
    「缺失符号 → 动态生成 stub（mov eax,120; ret）写进 IAT」。
- **协作式约束落点**：唯一能跑外部工作的点是 `mforms_paint_overlay()`（mforms.cpp:2278，每帧一次），
  它已有 `osapi_ic_job_tick(&budget=2)`（osapi.cpp:702）这种**每帧预算**范式 → D 类照抄这个模式。
- **句柄/槽复用**：`h_t` 句柄表（osapi.cpp，HK_* 21 种 kind 已预留，含 HK_ARENA/HK_SHM/HK_PERF）
  与 CLR slot（CLR_MAX_VMS=12）都可承载 AI 侧状态。

## 2026-11-13 D 类实现结构设计（用户已拍板三项决策）
**用户决策**：① 通道 = MKFS 数据盘双缓冲文件（ai_events.bin / ai_cmd.bin），**不补 inbound 网络**；
② 崩溃默认**保守**（记录现场→安全结束当前 PE→保活整机），提供开关让 AI 切**激进**（跳过崩溃指令）；
③ **第一版绝对禁止 AI 下发机器码**，AI 只能下发参数（选内置近似实现 / 分配哑句柄），由内核已有代码执行。
- **关键新发现（决定整个 D 类形态）**：`win32_run()` 是**同步阻塞**调用 —— `cmd_winapp`（kernel64.cpp:5322）
  → `win32_run` → 直接 `fn()` 调 PE 入口 → 一直跑到 PE 返回或崩。
  ⇒ **PE 运行期间主帧循环根本不转**，`mforms_paint_overlay()` 每帧轮询**永远等不到 PE 跑完**。
  ⇒ D1 观测若要"看着 PE 跑"，**必须把 PE 改成可挂起的协作式执行**（每 N 次 API 调用或每 T tick 让出一次），
     否则观测只能是"事后看"（PE 跑完/崩了才回写）。
  ⇒ 这与 A4（协作式线程）是**同一件事**：一个 fiber 式上下文切换同时解决 A4 与 D1 的实时性。
- **64 位 unwind 能力实测**：gcc 15.2 支持 64 位 `__attribute__((naked))`（实测 NAKED_64_OK），
  但仓库里**只有 32 位 `mini_setjmp/mini_longjmp`**（linux_compat.cpp:238/254，i386 版），
  kernel64 **没有任何 64 位 setjmp/longjmp** → D4 的"安全结束 PE"必须**新写 64 位版**
  （保存 rbx/rbp/r12-r15/rsp/rip）。
- **IDT 已支持 IST**：build_idt 用 `ist_flags = 0x8E00`（kernel64.cpp:1040）—— 0x8E00 是 DPL0 64 位
  interrupt gate 且 **IST=0**。要"崩了还能安全回内核"需要 **IST=1 + 独立 fault 栈**，
  否则 #PF 时处理器压栈可能本身就压坏（PE 栈已溢出时）。这是 D4 的硬前提。
- **数据盘写 API**：`kern_fs_create(name, data, len)`（kernel64.cpp:6126，extern "C"）→ 写 MKFS 数据盘。
  `mkfs.read(name, buf, cap)` 读。**VDI 是扇区粒度，不能原地改** → 必须双缓冲 + 序号。
- **命令调度**：新增 `cmd_compat()` 挂进 run_command 的 if-else 链（kernel64.cpp:6193+ 的既有风格）。
- **icall 注册**：mforms.cpp 的 `{ "NexOS.Forms.XXX::Method", fn }` 表（~136 条）；
  CLR_MAX_ICALLS=384，尚有余量。外部 AI 不走 CLR icall → **D 类接口应以内核命令 + 数据盘文件为主，
  icall 只作为托管侧（C#）的补充入口**。
