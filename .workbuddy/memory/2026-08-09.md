### 结论数据（务必记住，别再重复评估）
| | 体积 | vs 192KiB 上限 | 导入 | 覆盖率 |
|---|---|---|---|---|
| chrome.exe (launcher) | 3.87 MiB | **20.6x 超** | 360 fn / 16 DLL | 13.3% |
| chrome.dll (引擎本体) | **284.62 MiB** | **1518x 超** | 1316 fn / 67 DLL | 8.8% |

## 64→32 回切崩溃修复（栈地址冲突，2026-08-09 晚）

### 现象
用户在 64 位内核(`gui browser` 开 Chrome 后)再 `switch` 想回 32 位(IE)：QEMU 直接退出(BrokenPipe，无头测试 `test_switch_back`)。串口停在 `[K64] Switching to 32-bit kernel...` 之后、无 `Kernel32 loaded`。

### 根因（关键，非确定性崩溃的真相）
- `switch32to64.asm` 把 64 位内核的**长模式页表**放在 `PML4=0x90000 / PDPT=0x91000 / PD=0x92000 / PD2=0x93000`，并把 64 位内核**栈设在 `rsp=0x90000`**（entry64.asm:32 同设）。
- `cmd_switch32`(kernel64.cpp) 把 32 位 `kernel.bin` 加载到 `0x10000–0x90000`（[0x10000,0x90000)，最高 0x8FFFF）→ **覆盖了正在使用的 64 位内核栈**（栈向 0x8xxxx 下生长）。页表在 0x90000+ 恰好在加载区间外故安全；但栈被踩 → 返回帧/局部变量随机损坏 → **非确定性**崩溃（每次卡的位置都不同：i=256 / i=896 / i=960 / 首次 switch 直接炸乱码）。
- 注：`KERNEL32_SECTORS` 此前已从 256→1024（kernel.bin≈827 扇区），这是**必要但不充分**修复；真正致命的是低栈被覆盖。

### 修复
- `switch32to64.asm:196` 与 `entry64.asm:32`：`mov rsp, 0x90000` → `mov rsp, 0x1F0000`（kernel64 镜像尾 ~0x16C000 与堆 0x200000 之间的空闲区，仍在长模式身份映射的 0–1GB 内，且**高于** cmd_switch32 的加载区 0x90000）。页表保持 0x90000+（加载区间外，安全）。
- 顺手清掉 `cmd_switch32` 的调试插桩；移除 kernel64.cpp 里仅调试用的 `serial_putc/serial_hex/serial_putdec`（避免 `-Wall -Wextra` 未使用函数）。

### 验证
- `python3 tools/test_switch_back.py`：**PASS** —— 串口 `[K64] kernel.bin loaded at 0x10000` → `Kernel32 loaded, calling switch_to_32bit()` → `SFB[GDT] ring-0 + ring-3 segments + TSS loaded` → `[K1] kmain entered` → `[HW] Hardware Detection` → `[K] Command-line shell` → `[K5] Hello world written`。64→32 完整回到 32 位 shell，不再挂起/崩溃。
- `python3 tools/test_win64.py`：**PASS**（32→64 + PE 执行无回归；栈地址改动对两条进 64 位路径都生效，验证无误）。

## WinHost Browser 黑屏修复（C#，2026-08-09 晚）

### 现象
用户截图显示 WinHost（Windows 测试宿主）中打开 Browser 窗口后，客户区是一大块的黑色矩形；怀疑内存溢出或 32/64 位桌面相同。

### 根因
- **不是内存溢出**：RAM 64 MB 进度条正常；黑色是 .NET `WebBrowser` 控件在尚未加载任何文档时的默认背景色。
- WinHost 的 `ShellForm.SyncBrowser()` 创建 `WebBrowser` 后只做 `Visible=true`，没有主动导航；控件 uninitialized 背景为黑色。
- 截图中的 "Star Chrome" 标题与标签页是 WinHost 窗体本身，不是真实内核窗口。

### 32/64 位桌面为什么"一样"
- **64 位内核目前没有 C# 托管桌面**，`switch` 进 64 位后只有文本 shell。WinHost 只模拟 32 位托管桌面环境，因此用户看到的界面就是 32 位桌面；不存在"和 64 位一样"的问题，因为 64 位没有这套桌面。

### 修复
- `csharp/winhost/ShellForm.cs`：创建 `browserCtl` 后加 `browserCtl.Navigate("about:blank");`，让客户区初始为白色而非黑色。
- 纯 C# 改动，符合"GUI 改动优先 C#"规则。

### 验证
- `dotnet build WinHost.csproj`：**0 errors**（仅 nullable 警告，原有）。
- `WinHost.exe --shot browser_test.png 800 8`：**Browser 窗口客户区现为白色**，黑块消失。
