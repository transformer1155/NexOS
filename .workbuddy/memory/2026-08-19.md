## 修复 64 位内核 kmain64 早期 triple fault 重启循环

用户报"一看到蓝色就闪退"——根因是 `os.img` 启动后 32→64 位切换，64 位内核一进长模式就在 `boot_beacon` 处 triple fault 重启，陷入"蓝屏→重启"死循环；之前给的命令带 `-no-reboot`，把第一次重启变成 QEMU 立即退出，所以表现为"一蓝即闪退"。

### 根因
`boot_beacon`（`gui.cpp`）与 `diag_mark`（`kernel64.cpp`）的 `__x86_64__` 分支**只读 `framebuffer_phys64`（VbeInfo @ 0x5010）**。但 `stage2.asm` 的 BIOS 路径（`.vbe_settled` 正常路径行 618-619、`.vbe_no_bios` 路径行 493）**只填了 32 位 `framebuffer_phys`（@ 0x5000），从不写 0x5010**。于是 64 位侧 `fb64 == 0` → `fbva = 0` → `boot_beacon` 写空指针 `#PF`。串口看不到 `[DIAG-FAULT]` 是因为它直接 triple fault → 复位重启，不是被 `fault_common` 捕获的同步 #PF。

串口实证（`[K64-FB] fb64=0000000000000000 fb32=FD000000 w=1280 h=720 fmt=0`）：`fb64=0` 确认，32 位 LFB 物理地址 `0xFD000000` 才正确。

### 修复
`__x86_64__` 分支改为：`fb64 == 0 || fb64 > 0xFFFFFFFFULL` 时 **fallback 到 `0x5000` 的 32 位 LFB 物理地址**（BIOS 路径 LFB <4GiB，已被 `switch32to64.asm` 的 8×1GiB identity 页覆盖；仅当 `fb64` 是真正的 >4GiB UEFI GOP 地址时才走 `fb64` 原路径）。
- `gui.cpp` `boot_beacon`：fbva 计算（原 `fbva=(uintptr_t)fb64` 改为带 fallback）。
- `kernel64.cpp` `diag_mark`：同上（否则 step=2 之后的 M1 RED 仍会崩）。
- `kmain64` 内保留一行 `[K64-FB]` 自检信标（打印 fb64/fb32/w/h/fmt），对真机 LFB 排查有用，非临时垃圾日志。

### 验证（纯 Windows MSYS2 重编 + 无头 QEMU tcg）
- 重编 `os.img`（先 `rm -f build/*64.o` 避 stale；4387840 B，kernel64 519728 B @LBA2048）。
- 无头 `qemu-system-x86_64 -accel tcg -display none -serial file`（约 25s）：
  - 重启循环标记 `VBEFQ0SFBZ[K0] kmain entered` **13次/22s → 1次**（仅正常 boot 一次）。
  - DIAG 步号推进到 `step=333 gui_enter starting`（`render_all`/`enter_gui`/`mforms_boot`/`mforms_start OK`/`gui_enter` 全达）。
  - `[DIAG-FAULT]` 计数 = 0。
  - 结尾 `[M-POLL]`/`[GUI] render_all begin` —— 64 位 GUI 稳定运行。

### 关键坑（勿再踩）
- **误判教训**：之前的 `os_smoke.log` 其实是重启循环（step=1 后即 `VBEFQ0SFBZ[K0]` 重启），我当初误判为"正常"，务必看重启标记次数与完整 DIAG 步号序列，别只看"到了 Shell ready"。
- BIOS 路径 VbeInfo 只有 32 位 `framebuffer_phys`（0x5000）可靠；64 位侧**永远不要只信 `framebuffer_phys64`(0x5010)**，要带 32 位 fallback。
- 真机 UEFI（GOP LFB @0x4000000000）走 `switch32to64.compat_path` 已映射 >4GiB LFB，`fb64>4GiB` 分支原路径仍成立，本次修复不影响它。

## 64 位桌面"一闪一闪 + 崩溃重启循环"根因 = edge-test 诊断模式中间态（非信标）

## 登录面板"登录不了"根因 = 64 位 GuiCallbacks 结构错位（缺 write_file）+ 构建静默失效

## 开机启动界面显示项目 Logo（assets/Logo.png）

用户要求：开机启动界面显示 `assets/Logo.png`（1408×704 深蓝底 + 亮青 logo）。

### 实现
- **`tools/gen_logo.py`**：Logo.png 缩放到 256×128（保持 2:1）→ RGB565 → 生成 `logo.h`（`g_logo_data[32768]` + LOGO_W/LOGO_H，230KB 头文件）。
- **`gui.cpp gui_show_logo()`**（`#if __x86_64__` 内，避免 32 位 kernel 超 512KB）：复用 boot_beacon 的 VbeInfo@0x5000 定位（w/h/pitch/fmt/fb32/fb64，含 >4GB fallback）→ 全屏填深蓝底（1,20,53，像素打包与 boot_beacon 对齐：fmt0=BGRX32 / fmt1=RGBX32 / fmt3=RGB565 / else=RGBX32）→ 居中 blit logo。
- **`kernel64.cpp kmain64`**：`boot_beacon(GREEN)` 后调 `gui_show_logo()` + **64 位 rdtsc 忙等 ~2.5s**（`hold64 = 2500000ull*2500`）让 Logo 可见后再进登录屏。**32 位低位 rdtsc>>10 忙等在 QEMU tcg 下不可靠（回绕/时长错）→ 必须用 64 位 rdtsc**。
- Makefile：`gui.o/gui64.o: logo.h` 依赖。

### 关键坑（kernel64 扩容）
- **kernel64.bin 涨到 583KB 触发重启循环**：`kernel.cpp KERNEL64_SECTORS`（1024→**1280**，LBA2048+1280=3328=SFS 边界）与 **`switch32to64.asm KERNEL64_DWORDS`（1024*512/4→1280*512/4 = 640KB blit）** 都要同步——加载/拷贝不足会截断内核尾部（logo 数据在 .data 尾）→ triple fault 重启循环。
- 32 位 kernel 512KB 硬上限（stage2 只读 1024 扇区 + VGA MMIO hole）→ logo 只能进 64 位（`#if __x86_64__`）。

### 验证
- 串口确认 `[SPLASH] bg done`/`logo done` 执行、hold 生效；最终冒烟：锁屏+登录（root/admin uid=0）、reboot=1、faults=0、调试日志清零。
- **无头 screendump 像素验证受限**：QEMU `-vga std` 的 screendump 显示面格式与 32bpp BGRX 假设不符（深蓝底显示成绿 (0,128,0)），无头无法可靠验证颜色——**请用户图形窗口（-display gtk）或真机确认**（真机 GOP BGRX32 fmt=0 走正确分支）。
