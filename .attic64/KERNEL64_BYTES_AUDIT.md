# KERNEL64_BYTES 用法审计（只读）

**任务**：Lead 派发（零槽、纯静态）　**作者**：kernel-architect　**日期**：2026-11-02
**动机**：今天两次因为该常量引发的连带变化而误判（32 位 kernel.bin 出现 4 字节差异）。把它彻底搞清楚，未来不再重犯。

## 0. 结论

**该机制设计正确且有多重护栏，未发现缺陷。** 今天的 4 字节差异是它的**正常、可预测**的连带效应，
并且那份差异的**具体字节形态**现在可以被算术精确解释（见第 3 节）。

## 3. 今天那 4 字节差异的精确解释（本审计的直接收益）

实测：build/switch32to64.o 前后各差 **4 字节**，成两对，每对都是 CC F2 变为 0C F3。
两对 = **两处 mov ecx, KERNEL64_DWORDS**（第 1 节的使用者①②），每处 2 字节 —— 与「一个 imm32 的低两字节变化」完全一致。

算术（Lead 独立验证过数值；本审计解释**字节形态**）：
    旧 kernel64.bin = 1,035,056 B  ->  dwords = 258,764 = 0x3F2CC
    新 kernel64.bin = 1,035,312 B  ->  dwords = 258,828 = 0x3F30C
    差 = 64 dwords = 0x40

    0x3F2CC + 0x40 = 0x3F30C
      低字节：0xCC + 0x40 = 0x10C  -> 得 0x0C，进位 1
      次字节：0xF2 + 0x01 = 0xF3
    因此 imm32 的低两字节 CC F2 变为 0C F3，与实测逐位吻合（高两字节 03 00 不变）。

**结论：32 位 kernel.bin 每次都会因 kernel64 尺寸变化而改变这 4 个字节 —— 这是设计使然，不是回归。**
因此任何「32 位字节一致」的验收都必须**排除**这一项，改为对象级判据（承载改动的对象如 gui.o 不变）。

## 4. 残余风险（真实但可控，不主张立刻改）

1. **过期 kernel64.bin**：stat 会把**上一次**的大小烧进 32 位对象。Makefile 已把 kernel64.bin 列为
   switch32to64.o 的前置，但 vboxsf 的 mtime 不可靠。这正是全队那条规矩的由来：
   **镜像内嵌内容必须用 cmp 证明，不能靠 mtime。**
2. **向上取整多拷至多 3 字节**：无害，但值得知道（若将来目标区变成只读或边界敏感，需重新评估）。
3. **无 -D 的独立汇编**会得到 2 MiB 的旧默认值，与当前 KERNEL64_SECTORS*512 恰好相等。
   该相等关系靠人工维护 —— 建议在默认值处补一句注释指明「必须 == kernel.cpp 的 KERNEL64_SECTORS*512」。

## 5. 独立复核与更正（driver-network 初读 + Lead 复算；2026-11-02 追加）

driver-network 对本报告做独立初读，**2/9 项与我不同**；Lead 独立复算确认其成立。两条我都接受并更正如下。
（本节保留原第 2/4 节正文不改，以便读者看到「当时怎么写的、后来怎么被纠正的」。）

### 更正 #1：冻结的引用字节值过期 —— 应标注 read-at size+sha

我在第 3 节引用的 `b9 0c f3 03 00` 对应的是 **1,035,312 B** 那棵树；
而现在树里 kernel64.bin = **1,035,056 B**（0xFCB30），对应立即数是 `b9 cc f2 03 00`。

⇒ 机理结论**不变**（imm32 的低两字节随 dwords 变化），但**写死的字节值会随树漂移**。
规则：任何引用产物字节的诊断，必须同时记录 **read-at size + sha256**，否则它只是一张快照。
（本条与今天全队那条「镜像内嵌内容必须 cmp 证明、不能靠 mtime」同族：**引用值必须带出处**。）

### 更正 #2：第 2 节第 5 项「目标区间安全」的论证不完整 —— 最紧的界是 0x200000

**我原来的写法**：目标区间 `0x100000..0x300000`，远低于 `.lmboot`（>= 0x1800000）⇒ 安全。

**正确的最紧约束**来自 kernel.cpp:7641（运行时检查）：
    if (stage_phys < 0x00200000u || stage_phys + KERNEL64_SECTORS * 512 > IDENT_TOP) { ... bad stage addr ... }
即**暂存缓冲必须位于 0x200000 以上**（因为它自己就在被 blit 覆盖的那段窗口里）。
而 blit 的**目标末端** = `0x100000 + k64sz`；为不覆盖正在读取的源，它必须**低于暂存缓冲地址**。
暂存地址只有**下界** 0x200000 ⇒ **有效下界就是 0x200000**（最坏情况暂存恰好在 0x200000）。

当前实测：
    kernel64.bin      = 1,035,056 B = 0xFCB30
    目标末端           = 0x100000 + 0xFCB30 = **0x1FCB30**
    距 0x200000 的余量 = 0x200000 - 0x1FCB30 = **0x34D0 = 13,520 B**
    ⇒ 不是「远低于 .lmboot」，而是**只剩 13.5 KB**。

**若 kernel64 长到护栏允许的上限 2 MiB（= KERNEL64_SECTORS*512）**：
    目标末端 = 0x300000 ⇒ **越过 0x200000 达 1,048,576 B**
    ⇒ blit 会**覆盖自己正在读的源缓冲**（重叠拷贝）⇒ 尾部变成刚写下去的垃圾/零页
    —— 而「尾部零页」正是本文件第 1 节记录的、历史上真实发生过的失败模式（注释里的 1452 vs ~1620）。

### 为什么现有两道护栏**都拦不住**它（三层问题）

| # | 层 | 现状 | 问题 |
|---|---|---|---|
| 1 | 运行时检查（kernel.cpp:7641） | 约束 `stage_phys` 的地址 | **不随目标长度变化**：它证的是「暂存 >= 2 MiB」，而不是「目标末端 < 暂存」 |
| 2 | 构建护栏（Makefile:925-947） | 允许 k64sz 最大 = KERNEL64_SECTORS*512 = **2 MiB** | 这与「目标末端下界 0x200000」是**两个不同的约束**，而只有前者被强制 |
| 3 | 内存图打印（kernel.cpp:4134 / 4245） | 印「0x200000 - 0x2FFFFF Kernel heap (1 MiB)」 | **与常量矛盾**：kernel.cpp:3210 `HEAP_START = 0x10000000`（256 MiB）⇒ 打印是陈旧的 |

第 3 条尤其有害：**它正好会把做这项分析的人引到错误的界上** —— 读者会以为「堆从 0x200000 开始」，
于是把 0x200000 当成「堆的起点」而不是「暂存缓冲的下界」，从而得出与我原稿相同的错误结论。
（`kernel.cpp:4245 test_addr = 0x200000; // 2 MiB (heap)` 也是同一处陈旧引用。）

### 是否需要立为独立修复项：**是，建议高优先级**

理由：
  · 后果是**静默数据损坏**（重叠拷贝 ⇒ 尾部零页），不是崩溃；
  · 余量只有 **13,520 B**，而 kernel64.bin 今天已连续增长（991,696 -> 1,013,584 -> 1,034,864 -> 1,035,312 -> 1,035,056）；
  · **现有护栏结构上无法发现它**（一个查源、一个查源容量，没有查目标末端）；
  · 修复成本低，且可以让「约束可见」而不只是「靠人记得」。

建议修法（供排期参考，具体归属待定）：
  1. **构建期断言**：以同一个 k64sz 同时断言 `0x100000 + k64sz <= 0x200000`（即 k64sz <= 1 MiB），
     与现有的源侧护栏成对出现 —— 让「目标侧」也有一条机器判据；
  2. 或**运行时从 k64sz 反推暂存地址**（而不是只给它一个下界）：例如要求 `stage_phys >= 0x100000 + k64sz` 且 `>= 0x200000`，
     这样即使 k64sz 变大也不会自覆盖；
  3. 顺手修正 kernel.cpp:4134 / 4245 的陈旧内存图（它印的堆位置与 HEAP_START 矛盾）。

### 我接受这两条更正的说明

我在第 2 节把 0x300000 当成了安全上界 —— 那是**从 blit 目标长度反推的**，不是**从约束源反推的**。
正确的做法是：**先找强制约束（这里是 kernel.cpp:7641 的 stage_phys 下界），再从它推出有效上界**。
这正是今天反复出现的那类错误：**用自己想当然的界代替系统里真正生效的界。**

### 5.1 结论：是，立为独立修复项；落法选 (乙)（Lead + driver-network 共同定）

两个约束合并成一个不变量：

    0x100000 + k64sz <= STAGE_FLOOR        （当前 STAGE_FLOOR = 0x200000）
    <=>  k64sz <= STAGE_FLOOR - 0x100000   （当前 = 1 MiB）

**落法对比**：KERNEL64_SECTORS 在 kernel.cpp 有 6 处用途（7523 定义 / 7595 kmalloc 暂存区 /
7604 stage_end / 7641 与 0x200000 比较 / 7654 打印 / 7668 ATA 读扇区循环）。

| 落法 | 改动面 | 判定 |
|---|---|---|
| (甲) KERNEL64_SECTORS 4096 -> 2048 | 一处改动同时动 4 件事：暂存区、stage_end、读盘循环、打印 | **否决** |
| (乙) Makefile 新增独立的目标界断言 | 只动 Makefile；改一个命题，不碰暂存/读盘/打印 | **采纳** |

否决 (甲) 的核心理由（driver-network 提，比「注释指向」更本质）：
**KERNEL64_SECTORS 的语义是暂存窗口/读盘长度，它不是目标界**；
用 k64sz <= KERNEL64_SECTORS*512 去表达「目标不越过 STAGE_FLOOR」是**借用一个不相干的量**。
今天正因为这种「一个常数同时代表 4 个概念」吃过亏。

### 5.2 关键要求：上限值必须**从 kernel.cpp 读出**，不是复制

现有护栏已经做对了一半 —— secs 就是从源码 sed 读的：
    secs=$$(sed -n 's/^#define[[:space:]]*KERNEL64_SECTORS[[:space:]]*\([0-9]*\).*/\1/p' kernel.cpp | head -1)
照此办理，让 STAGE_FLOOR 也同源：

    1) kernel.cpp:7641 把裸常量 0x00200000u 提成具名宏（并让原处引用它）：
         #define STAGE_FLOOR  0x00200000u   /* the blit target must not reach this */
         if (stage_phys < STAGE_FLOOR || stage_phys + KERNEL64_SECTORS * 512 > IDENT_TOP) { ... }
    2) Makefile 用同样的 sed 读 STAGE_FLOOR，并算出目标界：
         floor=$$(sed -n 's/^#define[[:space:]]*STAGE_FLOOR[[:space:]]*\(0x[0-9a-fA-F]*\)u.*/\1/p' kernel.cpp | head -1)
         target_lim=$$(( floor - 0x100000 ))
         lim=min(secs*512, gap, target_lim)
    3) 新增一道独立分支（措辞要说清是**目标侧**，不是暂存侧）：
         if [ $$k64sz -gt $$target_lim ]; then ERROR: 目标末端会越过 STAGE_FLOOR; fi

**为什么这比「注释互相指向」强**：注释解决「人忘记看」，**取值同源解决「值漂移」**。
今天已经证明后者更可靠（KERNEL64_SECTORS 就是从 kernel.cpp 读的）。
照此做，STAGE_FLOOR 与护栏上限**在构造上不可能漂移**。

### 5.3 现场判据（改对了没有，一眼可看）

护栏打印 `K64 fit: <k64sz> / <lim> bytes (<spare> spare sectors)`：

    改前：lim = min(4096*512 = 2,097,152 ; gap = (SFS_LBA-2048)*512 = 2,097,152) = 2,097,152
          spare = (2,097,152 - 1,035,056) / 512 = **约 2,074 扇区**
    改后：lim = min(2,097,152 ; 2,097,152 ; target_lim = 0x200000-0x100000 = 1,048,576) = 1,048,576
          spare = (1,048,576 - 1,035,056) / 512 = **约 26 扇区**
    降幅 = **约 2,048 扇区**

⇒ 那行 spare 从约 2074 掉到约 26，**就是「改对了」的现场证据**（比读 diff 更直接）。
  同时说明：改后余量只剩约 13 KB —— 这条链已经很紧，应记入容量类风险台账。
  预期 KERNEL64_SECTORS **仍是 4096**（本次不动它）。
